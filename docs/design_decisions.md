# 设计决策记录

格式：背景 → 备选方案 → 最终选择 → 理由 → 代价与局限。按时间顺序追加，编号不复用。

---

## D1. 扩展上游的方式：继承和包装，不改源码

- **背景**：项目要清楚区分“A-RAG 原作者的工作”和“我的工作”，同时要在上游代码之上加计费、计时、轨迹记录等功能。
- **备选方案**：
  1. 直接修改 `src/arag/` 和 `scripts/`；
  2. 继承上游类，在子类里覆盖方法；
  3. 完全重写一套 Agent，只复用工具。
- **最终选择**：方案 2。`MeteredLLMClient(LLMClient)`、`MeteredBatchRunner(BatchRunner)`、`RecordingAgent(BaseAgent)`，上游 `Evaluator` 直接实例化复用。`scripts/` 下的脚本不是包，通过 `importlib` 按文件路径加载（`research_agent/upstream.py`）。
- **理由**：`git diff upstream/main -- src scripts` 为空，边界一目了然；上游的行为（提示词、工具、循环）保持原样，复现结果才有意义；以后合并上游更新时冲突最少。
- **代价与局限**：`MeteredLLMClient.chat` 为了加 `extra_body` 和重试，复制了上游 `chat` 构造请求体的约 10 行代码，上游改这段时需要同步。`BaseAgent.run` 是一个整体方法，没有钩子，以后改循环（规划、记忆）只能整体覆盖 `run`。

## D2. LLM：百炼 Qwen，主实验固定日期快照

- **背景**：方案选定阿里云百炼的 Qwen 系列（与后续 SFT 学生模型同家族）。开工时（2026-10-30）百炼上同时存在 `qwen-plus`（别名，指向 `qwen-plus-2025-12-01`，输入/输出 0.8/2 元每百万 token）和更新一代的 `qwen3.7-plus`（2/8 元）。
- **备选方案**：qwen-flash（最便宜）/ qwen-plus / qwen3.7-plus / qwen3-max（最贵）。
- **最终选择**：主实验用 plus 档，配置里写**日期快照名**而不是别名；调试用 flash 档。plus 档具体用哪一代，在阶段 0 的 5 题小样本实测后确定（见 experiments.md）。
- **理由**：
  - 多跳问答需要较强的推理和工具调用能力，flash 档太弱，A-RAG 与基线的差距可能被噪声淹没；max 档每 100 题要几十元，预算撑不起多张消融表。
  - 别名会被百炼静默升级到新版本，同一张对比表里前后跑的实验可能用了不同的模型。固定快照名才能保证可比。
- **代价与局限**：快照会下线，届时需要整表重跑。与论文的 GPT-4o-mini / GPT-5-mini 不是同一个模型，绝对数值不能直接对比，只能比相对趋势。

## D3. 关闭思考模式（`enable_thinking: false`）

- **背景**：Qwen 新模型是混合思考模型，开启思考后输出变贵，而且部分模型要求流式输出；上游 `LLMClient` 是非流式的。
- **备选方案**：开启 / 关闭。
- **最终选择**：关闭，并且在配置里**显式**写 `enable_thinking: false`，不依赖各模型不同的默认值。
- **理由**：成本更低；上游客户端可以直接用；与论文的 GPT-4o-mini（非推理模型）那一列对应。轨迹里没有 reasoning_content，以后转 SFT 数据格式也更简单。
- **代价与局限**：可能低估模型能力。思考模式可以留作以后的一个单独消融实验。

## D4. 固定裁判模型，不随 Agent 模型变化

- **背景**：上游 `eval.py` 用 `ARAG_MODEL` 环境变量作为裁判，也就是 Agent 用什么模型，裁判就用什么模型。论文固定用 GPT-5-mini 当裁判。
- **备选方案**：沿用上游（裁判 = Agent 模型）/ 固定一个裁判。
- **最终选择**：配置里单独的 `judge` 段，固定为 qwen-plus 快照，非思考模式，温度 0，`max_tokens=16`。
- **理由**：裁判是“尺子”。换 Agent 模型时如果尺子也跟着换，准确率的变化就分不清是 Agent 变了还是尺子变了。
- **代价与局限**：裁判与 Agent 是同一个模型时，可能存在“自己给自己打分”的偏差。上游裁判要求回复恰好是 `correct`，格式略有偏差就会误判。因此 `judge_meta.json` 记录了裁判回复的分布，用来检查有没有误判。

## D5. 成本统计口径：标价、人民币、计入隐式缓存

- **背景**：上游价格表没有 Qwen，而且是美元。百炼按单次请求的输入长度分档计价，隐式缓存命中的 token 按输入单价的 20% 计费，另有免费额度和限时折扣。
- **最终选择**：`configs/pricing_bailian.yaml` 按快照名记录分档标价（注明来源和核实日期），按每次请求的 `prompt_tokens` 选档，缓存部分乘 0.2。免费额度和限时折扣不计入。
- **理由**：按标价算出的是**上界**，在不同时期跑的实验之间可比，不受折扣活动影响。缓存折扣是 Agent 场景的真实特性（每轮重发相同前缀），必须计入，否则会高估成本。
- **代价与局限**：与阿里云账单上的实际扣费会有差距（免费额度期间账单可能是 0）。价格调整时需要更新 YAML。

## D6. LLM 调用失败时带退避重试

- **背景**：上游 `BaseAgent` 遇到 LLM 异常直接 `break`，随后强制作答，结果被标成“达到最大轮数”。并发跑题时偶发的 429 限流会让这道题直接变成错题。
- **最终选择**：对 429 / 5xx / 超时 / 连接错误做指数退避重试（基数 2 秒，最多重试 4 次，带随机抖动）；4xx 参数错误立即失败。最终失败的调用记入 `llm_errors`，终止原因标为 `llm_error`。
- **理由**：瞬时的基础设施错误不应该算作 Agent 的能力问题。
- **代价与局限**：重试会拉长那道题的耗时，延迟统计里会包含重试等待的时间。

## D7. 评测子集：均匀随机抽样，固定种子，并且与调试集不相交

- **背景**：预算限制下不能每次都跑完整的 1000 题。
- **备选方案**：取前 100 题 / 随机抽样 / 按跳数分层抽样。
- **最终选择**：从 1000 题中用 `random.Random(42)` 抽 100 题，保持原顺序，文件和元数据（源文件 sha256、种子、题目 id）一起提交到 `data/subsets/`。调试用的 5 题子集（种子 7）与这 100 题不相交。
- **理由**：数据集的顺序可能有偏（前面的题可能集中在某种题型），取前 100 题不可靠；固定种子加源文件哈希，任何人都能复现同一个子集；调试集与评测集分开，可以避免在评测集上调参。
- **代价与局限**：没有分层，100 题里 4 跳题只有 11 道（全量中占 16.6%），按跳数细分时样本太少。100 题的准确率标准误大约是 ±5 个百分点，差距小于这个量级的结论不可靠。

## D8. 本地 GPU 环境：固定 torch 的 CUDA 12.8 构建

- **背景**：Windows 驱动 572.70 最高支持 CUDA 12.8；`uv sync` 默认装的 torch 2.15 是 CUDA 13.2 构建，WSL2 中 `torch.cuda.is_available()` 为 False。
- **备选方案**：升级 Windows 显卡驱动 / 固定旧版 torch。
- **最终选择**：在 `pyproject.toml` 里把 torch 指向 PyTorch 官方 cu128 源（得到 torch 2.11.0+cu128）。
- **理由**：不需要改动 Windows 系统，可复现；cu128 构建在更新的驱动上也能运行。
- **代价与局限**：torch 停在 2.11。以后需要较新的 vLLM（阶段 7）时可能还是得升级驱动，届时去掉这个固定。
