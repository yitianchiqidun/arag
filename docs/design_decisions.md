# 设计决策记录

格式：背景 → 备选方案 → 最终选择 → 理由 → 代价与局限。按时间顺序追加，编号不复用。

---

## D1. 扩展上游的方式：继承和包装，不改源码

- **背景**：项目要清楚区分“A-RAG 原作者的工作”和“我的工作”，同时要在上游代码之上加计费、计时、轨迹记录等功能。
- **备选方案**：
  1. 直接修改 `src/arag/` 和 `scripts/`；
  2. 继承上游类，在子类里覆盖方法；
  3. 完全重写一套 Agent，只复用工具。
- **最终选择**：方案 2。`MeteredLLMClient(LLMClient)`、`MeteredBatchRunner(BatchRunner)`、`RecordingAgent(BaseAgent)`，上游 `Evaluator` 直接实例化复用。`scripts/` 下的脚本不是包，通过 `importlib` 按文件路径加载（`research_agent/upstream.py`）。
- **理由**：`git diff upstream/main -- src scripts` 为空，边界一目了然；上游的行为（提示词、工具、循环）保持原样，复现结果才有意义；以后合并上游更新时冲突最少。
- **代价与局限**：`MeteredLLMClient.chat` 为了加 `extra_body` 和重试，复制了上游 `chat` 构造请求体的约 10 行代码，上游改这段时需要同步。`BaseAgent.run` 是一个整体方法，没有钩子，以后改循环（规划、记忆）只能整体覆盖 `run`。

## D2. LLM：百炼 Qwen，主实验固定日期快照

- **背景**：方案选定阿里云百炼的 Qwen 系列（与后续 SFT 学生模型同家族）。开工时（2026-10-30）百炼上同时存在 `qwen-plus`（别名，指向 `qwen-plus-2025-12-01`，输入/输出 0.8/2 元每百万 token）和更新一代的 `qwen3.7-plus`（2/8 元）。
- **备选方案**：qwen-flash（最便宜）/ qwen-plus / qwen3.7-plus / qwen3-max（最贵）。
- **最终选择**：主实验用 plus 档，配置里写**日期快照名**而不是别名；调试用 flash 档。两代 plus 都在 MuSiQue-100 上跑了一遍（见 experiments.md）：qwen3.7-plus 的 LLM-Acc 为 68%，qwen-plus-2025-12-01 为 57%（配对检验 p = 0.035）；每 100 题花费分别为 6.2 元和 2.2 元。**2026-10-30 确定主模型为 `qwen3.7-plus-2026-05-26`**（主配置 `configs/musique_qwen37_plus.yaml`），阶段 1 起所有对比表都用它；`qwen-plus-2025-12-01` 只保留为裁判。
- **理由**：
  - 多跳问答需要较强的推理和工具调用能力，flash 档太弱，A-RAG 与基线的差距可能被噪声淹没；max 档每 100 题要几十元，预算撑不起多张消融表。
  - 别名会被百炼静默升级到新版本，同一张对比表里前后跑的实验可能用了不同的模型。固定快照名才能保证可比。
  - 3.7-plus 准确率显著更高（+11 个百分点，p = 0.035），更接近论文 GPT-5-mini 的水平，和论文的消融结论更有可比性；每 100 题 6.2 元，在预算内能跑完阶段 1 的整张对比表。
- **代价与局限**：快照会下线，届时需要整表重跑。与论文的 GPT-4o-mini / GPT-5-mini 不是同一个模型，绝对数值不能直接对比，只能比相对趋势。3.7-plus 每题成本约为 plus-1201 的 2.8 倍，并且有 22% 的题跑满 15 轮，后续实验的成本和轮数上限都受它影响。

## D3. 关闭思考模式（`enable_thinking: false`）

- **背景**：Qwen 新模型是混合思考模型，开启思考后输出变贵，而且部分模型要求流式输出；上游 `LLMClient` 是非流式的。
- **备选方案**：开启 / 关闭。
- **最终选择**：关闭，并且在配置里**显式**写 `enable_thinking: false`，不依赖各模型不同的默认值。
- **理由**：成本更低；上游客户端可以直接用；与论文的 GPT-4o-mini（非推理模型）那一列对应。轨迹里没有 reasoning_content，以后转 SFT 数据格式也更简单。
- **代价与局限**：可能低估模型能力。思考模式可以留作以后的一个单独消融实验。

## D4. 固定裁判模型，不随 Agent 模型变化

- **背景**：上游 `eval.py` 用 `ARAG_MODEL` 环境变量作为裁判，也就是 Agent 用什么模型，裁判就用什么模型。论文固定用 GPT-5-mini 当裁判。
- **备选方案**：沿用上游（裁判 = Agent 模型）/ 固定一个裁判。
- **最终选择**：配置里单独的 `judge` 段，固定为 qwen-plus 快照，非思考模式，温度 0，`max_tokens=16`。
- **理由**：裁判是“尺子”。换 Agent 模型时如果尺子也跟着换，准确率的变化就分不清是 Agent 变了还是尺子变了。
- **代价与局限**：裁判与 Agent 是同一个模型时，可能存在“自己给自己打分”的偏差。上游裁判要求回复恰好是 `correct`，格式略有偏差就会误判。因此 `judge_meta.json` 记录了裁判回复的分布，用来检查有没有误判。

## D5. 成本统计口径：标价、人民币、计入隐式缓存

- **背景**：上游价格表没有 Qwen，而且是美元。百炼按单次请求的输入长度分档计价，隐式缓存命中的 token 按输入单价的 20% 计费，另有免费额度和限时折扣。
- **最终选择**：`configs/pricing_bailian.yaml` 按快照名记录分档标价（注明来源和核实日期），按每次请求的 `prompt_tokens` 选档，缓存部分乘 0.2。免费额度和限时折扣不计入。
- **理由**：按标价算出的是**上界**，在不同时期跑的实验之间可比，不受折扣活动影响。缓存折扣是 Agent 场景的真实特性（每轮重发相同前缀），必须计入，否则会高估成本。
- **代价与局限**：与阿里云账单上的实际扣费会有差距（免费额度期间账单可能是 0）。价格调整时需要更新 YAML。

## D6. LLM 调用失败时带退避重试

- **背景**：上游 `BaseAgent` 遇到 LLM 异常直接 `break`，随后强制作答，结果被标成“达到最大轮数”。并发跑题时偶发的 429 限流会让这道题直接变成错题。
- **最终选择**：对 429 / 5xx / 超时 / 连接错误做指数退避重试（基数 2 秒，最多重试 4 次，带随机抖动）；4xx 参数错误立即失败。最终失败的调用记入 `llm_errors`，终止原因标为 `llm_error`。
- **理由**：瞬时的基础设施错误不应该算作 Agent 的能力问题。
- **代价与局限**：重试会拉长那道题的耗时，延迟统计里会包含重试等待的时间。

## D7. 评测子集：均匀随机抽样，固定种子，并且与调试集不相交

- **背景**：预算限制下不能每次都跑完整的 1000 题。
- **备选方案**：取前 100 题 / 随机抽样 / 按跳数分层抽样。
- **最终选择**：从 1000 题中用 `random.Random(42)` 抽 100 题，保持原顺序，文件和元数据（源文件 sha256、种子、题目 id）一起提交到 `data/subsets/`。调试用的 5 题子集（种子 7）与这 100 题不相交。
- **理由**：数据集的顺序可能有偏（前面的题可能集中在某种题型），取前 100 题不可靠；固定种子加源文件哈希，任何人都能复现同一个子集；调试集与评测集分开，可以避免在评测集上调参。
- **代价与局限**：没有分层，100 题里 4 跳题只有 11 道（全量中占 16.6%），按跳数细分时样本太少。100 题的准确率标准误大约是 ±5 个百分点，差距小于这个量级的结论不可靠。

## D8. 本地 GPU 环境：固定 torch 的 CUDA 12.8 构建

- **背景**：Windows 驱动 572.70 最高支持 CUDA 12.8；`uv sync` 默认装的 torch 2.15 是 CUDA 13.2 构建，WSL2 中 `torch.cuda.is_available()` 为 False。
- **备选方案**：升级 Windows 显卡驱动 / 固定旧版 torch。
- **最终选择**：在 `pyproject.toml` 里把 torch 指向 PyTorch 官方 cu128 源（得到 torch 2.11.0+cu128）。
- **理由**：不需要改动 Windows 系统，可复现；cu128 构建在更新的驱动上也能运行。
- **代价与局限**：torch 停在 2.11。以后需要较新的 vLLM（阶段 9 的本地模型部署）时可能还是得升级驱动，届时去掉这个固定。

## D9. 主指标用 LLM-Acc，Cont-Acc 只作参考

- **背景**：上游同时报告 LLM-Acc（LLM 裁判）和 Cont-Acc（标准答案是否是预测的子串）。阶段 0 中两者相差 13 个百分点，方向与论文相反。
- **做法**：人工核对了全部 42 道两种指标结论不一致的题（experiments.md 阶段 0 一节）。
- **发现**：裁判在 83% 的分歧题上判断正确，错误都是“过严”，没有把错答案判对的情况；Cont-Acc 因为答案啰嗦（中位数约 1000 字符），在 35 道分歧题中大多是误判为对。
- **最终选择**：以 LLM-Acc 为主要指标，所有结论基于它得出；Cont-Acc 照常报告，但不用来下结论。
- **理由**：一个指标首先要验证它能不能“量准”。Cont-Acc 的误判与答案长度相关，而阶段 5 的改动（例如规划、笔记）很可能改变答案长度，用它做对比会把“答案变长”误当成“变准了”。
- **代价与局限**：LLM 裁判有成本（每 100 题约 0.03 元，可以忽略），并且约低估 2–3 个百分点。如果以后要让 Cont-Acc 可用，可以让 Agent 额外输出一个简短的“最终答案”字段。但这会改动上游提示词，留到阶段 1 再评估。

## D10. 普通 RAG 基线：照论文实现，块级向量单独建索引

- **背景**：阶段 1 需要一个“一次向量检索取 top-k，再生成答案”的基线。上游仓库没有提供基线脚本（README 的 TODO 里列着）。论文对 Naive RAG 的描述是：Qwen3-Embedding-0.6B、top-k = 5、约 1000 token 的块、Figure 6 的提示词模板，没有说明块怎么拼接。
- **备选方案**：
  1. 复用 A-RAG 的句子级索引，取每个块里最相似句子的分数作为块的分数；
  2. 对整块文本单独建一份块级向量索引；
  3. 让 A-RAG 只保留 semantic_search 一个工具（这是另一种东西，论文叫 A-RAG (Naive)，仍然是 Agent）。
- **最终选择**：方案 2。整块编码，归一化，不加 query instruction（与上游 `build_index.py` 和 semantic_search 一致），缓存在 `data/musique/index/chunk_index.npz`，元数据里记录模型名和 chunks.json 的哈希，任一变化就重建。提示词按 Figure 6：第一句作为 system，其余作为 user；块按 `[Chunk id]\n正文` 用空行拼接。代码：`research_agent/baselines/naive_rag.py`。
- **理由**：“普通 RAG”的通行做法就是块级检索，论文报告的 Naive RAG 检索量（MuSiQue 5,387 token）也正好约等于 5 个整块（我们的块平均 1,079 token）。方案 1 实际上是把 semantic_search 的排序拿来用，会让基线和 A-RAG 共享同一个检索器，削弱对比的意义。
- **代价与局限**：多了一份索引（1,354 × 1024 维，约 5.5 MB）。块级向量对约 1000 token 的长文本是“平均语义”，可能不如句子级精确，这正是论文想说明的问题之一，但也意味着基线的强弱依赖嵌入模型对长文本的处理能力。为了不在 6 GB 显存上加载第二份嵌入模型，基线复用 semantic_search 已加载的模型（`shared_semantic_tool`）。

## D11. 工具消融：配置开关，提示词和工具描述跟着工具集走

- **背景**：论文的消融有三个：w/o Keyword Search、w/o Semantic Search（直接去掉对应工具），w/o Chunk Read（“把两个搜索工具的片段结果换成完整块文本，并去掉 read_chunk”）。上游没有提供消融接口，系统提示词里写死了三个工具名。
- **备选方案**：
  1. 只在注册表里少注册一个工具，提示词不动；
  2. 少注册工具，同时从提示词里删掉对应的那一行；w/o Chunk Read 再改策略句和搜索工具的返回说明。
- **最终选择**：方案 2，开关是 `agent.tools` 和 `agent.search_result: snippet | full_chunk`。提示词由上游文件派生（`research_agent/agent/prompt.py`），每处修改都断言目标文本存在，上游提示词一变就报错；完整配置下输出与上游文件逐字节相同（有单元测试）。w/o Chunk Read 用包装器 `FullChunkSearch` 实现（`research_agent/agent/tools.py`）：排序仍交给上游搜索工具，只把结果换成整块文本。另外两个细节：
  - **全文去重**：已经展示过全文的块再次命中时，只返回“之前已展示”的标记，和上游 read_chunk 的去重逻辑一样。这样 w/o Chunk Read 与完整版的唯一差别是“全文由谁挑选”（搜索排序 vs 模型），而不是“有没有去重”。论文没有说明这一点。
  - **缺索引报错**：上游在找不到句子索引时会静默去掉 semantic_search，这会让完整版在不知不觉中变成消融版。这里改为直接报错。
- **理由**：提示词里列出一个不存在的工具，模型可能会去调用它，得到 “Tool not found” 后浪费轮数，测出来的就不只是“少一个工具”的效果了。消融只应改变一个变量。
- **代价与局限**：其余工具描述里仍然提到被去掉的工具（例如 semantic_search 的描述写着“当关键词搜索失败时使用”），只删除了提示词里的工具列表行，没有逐句改写所有描述。这是为了让改动尽量小，也和论文“直接去掉工具”的说法一致。

## D12. 一张对比表里的实验靠构造保证可比

- **背景**：工作规则要求同一张表里的实验必须使用相同的模型和参数。手工维护多份配置文件很容易漏改某个参数。
- **最终选择**：用“实验套件” YAML（`configs/suites/`）描述一整张表：每个变体 = 一个基础配置 + 少量覆盖项。生成对比表时（`research_agent/eval/compare.py`），从每个运行目录的 `run_meta.json` 里读出完整配置，展开后逐项比较：只允许 `method`、`agent.tools`、`agent.search_result`、`naive_rag.*` 不同；模型快照、温度、轮数上限、题目文件哈希、并发数等任何一项不同，都直接报错。表格下方列出每一行与其他行不同的设置。
- **理由**：可比性由数据检查保证，不靠人记。这项检查也能防住“重跑时换了模型别名”或“用错了子集”这类错误。
- **代价与局限**：代码版本（git commit）允许不同，只在表格里注明。阶段 0 的旧运行可以直接放进表里（在套件里写 `run_dir`），前提是这些运行的配置通过上面的检查。

## D13. 对比用全部题目上的 LLM-Acc，配对做精确 McNemar 检验

- **背景**：100 题上单个准确率的 95% 置信区间约为 ±9 个百分点，而论文里的消融差距只有 0.5–4.7 个百分点。两个准确率的置信区间是否重叠，并不是判断差异的正确方法：同一批题目上的两次运行是配对数据。
- **最终选择**：
  - 对比表里的准确率用“全部题目”作分母（`llm_acc_all`），空答案和报错都算错。上游 `eval.py` 的分母只算有答案的题，会让报错多的变体占便宜。阶段 0 两次运行都没有报错，两种口径相同。
  - 每个变体都与参考行（A-RAG Full）逐题配对，只看“一个对、一个错”的题，做双侧精确 McNemar 检验，报告 p 值和两类不一致题的数量。
- **理由**：配对检验消除了“题目难度”这个最大的方差来源，比两个独立比例的检验灵敏得多。精确检验适用于不一致题很少（几道到十几道）的情况。
- **代价与局限**：100 题仍然只能可靠地检出约 10 个百分点以上的差距。表中 p > 0.05 的差异只能说明“没有检出”，不能说明“没有差异”。要验证论文中几个百分点的消融差距，需要更大的子集（例如 300 题，花费约为 3 倍）。

## D14. 新指标的口径：重复读取率与重复检索率

- **背景**：方案要求统计“重复读取率：同一文本块被重复读取的比例”。
- **最终选择**：
  - **重复读取率** = 请求全文时，已经展示过全文的块数 ÷ 请求全文的块总数，在全部题目上合并计算（微平均）。完整版的“请求全文”是 read_chunk；w/o Chunk Read 版本是返回全文的搜索。两者都记录 `new_chunks_count` 和 `already_read_count`，所以用同一个公式计算。
  - 另外增加 **重复检索率**：同一题内，与之前某次搜索完全相同的搜索（同一工具、关键词集合或查询文本相同、top_k 也相同，忽略大小写和空白）所占的比例。这对应阶段 2 bad case 标签里的“重复检索”。
  - **达到最大轮数的比例** 只统计 `termination == max_loops`，LLM 报错导致的提前结束单独记为 `llm_error`（D6）。
  - 按跳数分组的准确率从 MuSiQue 题目编号里解析（`musique_3hop1__…`）。
- **理由**：上游 read_chunk 对已读的块只返回一句提示，不会重复计入 retrieved tokens，因此“重复读取”在上游指标里是看不见的，但它仍然浪费一轮 LLM 调用。阶段 0 的数据显示，3.7-plus 有 8.3% 的读块请求读的是已经读过的块。
- **代价与局限**：重复检索只识别完全相同的搜索。换个说法再搜一遍同一件事（语义重复）不会被计入，需要等阶段 2 的轨迹分析来补充。另外，w/o Chunk Read 版本的“重复读取”是搜索结果再次命中已展示的块，由排序决定，不是模型主动重读，而且这些块不重复计 token。它和完整版的重复读取率含义不同，不能直接比较（阶段 1 中两者分别为 31.3% 和 9.7%）。

## D15. 暂不做 LLM 响应缓存（方案中的可选项）

- **背景**：方案把“相同请求不重复计费的响应缓存”列为可选项。
- **最终选择**：阶段 1 不做。
- **理由**：
  1. 对比表里的每个变体请求都不同，缓存命中不了；
  2. 中断后续跑已经由上游 BatchRunner 的断点续跑（跳过已完成的题目）解决，判分和汇总可以单独重跑，不调用 Agent；
  3. 缓存命中会让延迟和花费指标失真，需要额外区分“真实调用”和“缓存命中”。
- **代价与局限**：如果以后需要反复重放同一批请求（例如阶段 2 调试轨迹回放、阶段 5 修改汇总逻辑），再按 payload 哈希加一层磁盘缓存，并在记录里标记命中。D9 中提到的“让 Agent 额外输出简短最终答案以改善 Cont-Acc”，阶段 1 也不做：它需要修改提示词，会让结果与论文和阶段 0 不可比。

## D16. 内容审核拦截按答错计，另做排除后的敏感性分析

- **背景**：阶段 1 的 w/o Chunk Read 变体有 5 道题的请求被百炼内容审核拦截（HTTP 400 `DataInspectionFailed`）。这时 Agent 循环中断，强制作答也被拦截，最终输出 `Error: ...`。其他变体一次都没有被拦截。
- **备选方案**：
  1. 按答错计入主表；
  2. 从所有变体中剔除这 5 题，主表只用剩下的 95 题；
  3. 换一个审核更宽松的模型重跑这几题。
- **最终选择**：方案 1 作为主表口径，同时报告方案 2 的结果作为敏感性分析（experiments.md 阶段 1 一节）。客户端不对 400 重试（D6 的规则不变）。
- **理由**：被拦截是“整块返回”这个设计在国内云 API 上真实会遇到的失败：上下文里堆了大量原文，更容易触发审核。把它算作失败，才反映该设计在这个部署环境下的真实表现。剔除这些题则相当于只在“对它友好”的题上比较。方案 3 换了模型，违反同一张表用同一模型的规则。
- **代价与局限**：主表里 w/o Chunk Read 的准确率包含了平台因素，并不是纯粹的“检索接口”效应。排除这 5 题后，结论从“低 2 个百分点”变成“高 2 个百分点”，两者都不显著。审核的具体触发规则不透明，换一个时间或换一个快照，结果可能不同。阶段 6 的服务需要处理这类错误：向用户返回明确的“内容被平台拦截”，而不是笼统的报错。


## D17. 评测规模的估算：重跑噪声与样本量（2026-11-02 确认）

- **背景**：阶段 1 中，同一配置在同一 100 题上跑两次，准确率差 3 个百分点，有 11 道题两次结论相反（64 道两次都对，25 道两次都错）。按 D13 的配对检验，100 题只能可靠地检出约 10 个百分点以上的差距。后续的改进很可能只有几个百分点；“准确率不能显著下降”这类要求在 100 题上几乎必然成立，因为本来就检不出差异。所以在做对比之前，要先估算需要多少题。

- **怎么估算**：一道题在某个方法下答对的概率记为 p，两种方法差 d = p_A − p_B。估计 d 时有两个噪声来源：
  - **题间差异 σ²_b**：同一个改动在有的题上有帮助，在有的题上有害。这一项只能靠增加题目来降低。
  - **重跑噪声 σ²_w**：LLM 在 temperature 0 下也不完全确定，裁判也会有波动。这一项靠增加题目或者重复运行都能降低。

  n 道题、每个方法各跑 k 次时，Var(d̂) ≈ (σ²_b + σ²_w / k) / n。显著性水平 0.05（双侧）、检验力 80% 时，最小可检出差距 ≈ 2.8 × √Var。用阶段 1 的逐题数据估计两项参数：
  - **σ²_w ≈ 0.11**：两次 Full 运行的不一致率是 11/100，95% 置信区间 6%–19%。
  - **σ²_b**：等于“某消融与两次 Full 的平均不一致率”减去 σ²_w。
    - w/o semantic：0.095 − 0.11 ≈ 0，它和 Full 的差别与重跑一次 Full 的差别一样大；
    - w/o read_chunk：约 0.025；
    - w/o keyword：约 0.085；
    - 普通 RAG：约 0.31。
  - 会改变 Agent 行为的改动（路由、上下文压缩等），σ²_b 估计在 0.05–0.10 之间。

- **备选方案**（表中“花费”为 MuSiQue 上每个变体的标价，按 Full 的单价 6.38 元 / 100 题估算，含裁判）：

  | 方案 | 每个变体花费 | 最小可检出差距（σ²_b = 0 / 0.05 / 0.10） |
  | --- | ---: | --- |
  | 100 题 × 1 次（阶段 1 现状） | 6.4 元 | 9.3 / 11.2 / 12.8 pp |
  | 100 题 × 2 次 | 12.8 元 | 6.6 / 9.1 / 11.0 pp |
  | 100 题 × 3 次 | 19.1 元 | 5.4 / 8.2 / 10.4 pp |
  | 200 题 × 1 次 | 12.8 元 | 6.6 / 7.9 / 9.1 pp |
  | 300 题 × 1 次 | 19.1 元 | 5.4 / 6.5 / 7.4 pp |
  | 500 题 × 1 次 | 31.9 元 | 4.2 / 5.0 / 5.7 pp |

  σ²_w 取置信区间两端（0.06 或 0.19）时，300 × 1 的可检出差距在 4.0–8.7 pp 之间。

- **最终选择**：
  1. 预算有限时**增加题目，而不是重复运行**：每个变体在每道题上只跑一次。
  2. 检验沿用 D13 的精确 McNemar，另外在对比表里补一列“配对差值的 95% 置信区间”。
  3. “准确率不能下降”这类要求改为非劣效判断：置信区间下界高于事先定好的界限才算通过。界限按评测集的规模用上面的公式算出（例如 300 题时，检验力 80% 对应约 −6 个百分点），并且要在看到结果之前定下来。

- **理由**：
  1. **花费相同时，n × 1 总是不比 (n/k) × k 差**。两者调用量一样，但重复运行只能平均掉重跑噪声，题间差异那一项一点也不会减少。只要改动在不同题上的效果不一样（σ²_b > 0，阶段 1 的 w/o keyword 就已经是 0.085），增加题目就更好。
  2. **每题只跑一次时，现有的检验方法可以直接用**。重复运行时，同一道题的几次结果不独立，McNemar 不再适用，要改用“按题汇总后做置换检验或 bootstrap”，还得改代码。

- **代价与局限**：
  - **检出能力**：几百道题也只能可靠地检出约 6 个百分点以上的差距，论文里 0.5–4.7 个百分点的消融差距依然检不出。对比表要同时给出置信区间，不能只看 p 值。
  - **σ²_w 的估计**：最初只来自一对运行。阶段 2 重跑 Full 后（experiments.md 阶段 2 一节），三对运行的不一致率分别是 11%、10%、11%，平均 10.7%，与 0.11 一致，上面的估算不需要修改。换了评测集和模型后，σ²_w 要重新估计。
  - **非劣效界限偏宽**：300 题时 −6 pp 已经是检验力能达到 80% 的界限；要收紧到 −4 pp，大约需要 700 题。
  - **延迟**：要比较延迟的变体应在同一时段连续运行，否则 API 负载会让延迟无法比较（阶段 1 中同一配置的 P50 分别为 40.5 秒和 28.8 秒）。准确率不受这一点影响。
  - **已实现**：
    - `subset --exclude FILE` 在抽样前把已有子集的题目从候选池中去掉，元数据里记录被排除的文件及其 sha256；不带 `--exclude` 时抽样结果与以前逐字节相同。
    - 对比表新增“95% CI of Δ”列（Newcombe 配对区间，`metrics.paired_diff_ci`）。
    - 阶段 1 的表已离线重算：w/o keyword 的区间是 [−14.0, +4.1]，说明 100 题上“不显著”能容纳多大的真实差距。

## D18. 账户级 API 错误直接中止整个运行

- **背景**：上游 `BatchRunner` 遇到某道题报错时，会把 `Error: ...` 当作答案写进 `predictions.jsonl`，续跑时把这道题当作已完成跳过。如果余额在运行中途耗尽，剩下的每道题都会很快失败，并被记成答错。这样的运行看起来是完整的，结果却被污染了，而且续跑也不会补跑这些题。
- **备选方案**：
  1. 运行前查询余额：百炼的 API key 没有查询余额的接口，需要阿里云 AccessKey 调用费用中心 API，引入新的密钥，不值得；
  2. 任何错误都中止：内容审核拦截（D16）是单题现象，不应该让整个运行停下来；
  3. 只对账户级错误中止。
- **最终选择**：方案 3。
  - `MeteredLLMClient` 把 HTTP 401、403、404 以及错误码 `Arrearage`（欠费）、`InvalidApiKey` 识别为 `AccountError`，不重试。
  - 运行器发现某道题遇到这类错误时：这道题不写结果；之后的题不再调用 API，直接跳过；运行结束时抛出 `RunAborted`。修好账户后，用同一条命令续跑。
  - 另外，运行结束时如果有题没写进结果（上游只打印 `Error processing`），会直接报错，不再静默缺题。
- **理由**：出错时宁可停下来，也不要产出一份看似完整的错误结果。续跑机制本来就存在，只要保证被账户错误影响的题不写入，续跑就能自然补上。
- **代价与局限**：错误码列表来自百炼文档和经验，平台新增的账户级错误码仍会被当作单题错误。正在运行的其他题如果在同一时刻失败，也不会写入，续跑时会重跑，可能多花几题的钱。

## D19. 轨迹记录：两个钩子 + 一次 LLM 调用为一步

- **背景**：方案要求按步记录思考、工具调用、token、耗时、每次调用时上下文的大小，以及完整的 messages（之后转成 SFT 数据）。上游 `BaseAgent.run` 只返回工具调用列表，messages 是 `run()` 里的局部变量，拿不到。
- **备选方案**：
  1. 复制一份 `BaseAgent.run`，在里面埋点：代码重复，上游一改就悄悄失效；
  2. 修改上游 `run()`：违反“不改上游代码”的原则；
  3. 在 Agent 已经调用的两个对象上挂钩子：LLM 客户端和工具注册表。
- **最终选择**：方案 3。
  - `MeteredLLMClient.observer`：每次调用后拿到“实际发出的 messages、工具定义、用量记录、模型回复”。
  - `TimedToolRegistry`：每个 Agent 一个，包装共享的工具注册表，记录每次工具调用的耗时。
  - `TraceRecorder.build` 按顺序把它们和上游返回的工具调用列表对齐，生成 `Trajectory`，逐题写入运行目录下的 `trajectories.jsonl`。
  - **一步 = 一次 LLM 调用**，加上这次回复请求的所有工具调用。模型偶尔会在一次回复里并行调用多个工具（阶段 0/1 的 2,520 轮里有 2 次），所以方案里的单个 `tool_name` 改成了 `tool_calls` 列表。
  - 字段名沿用 API 的叫法：`prompt_tokens` 就是方案里的 `tokens_in`，`completion_tokens` 就是 `tokens_out`。
  - 每一步的步类型分为：调用工具、作答、强制作答、LLM 报错、向量检索（普通 RAG）。
  - messages 只保存最后一次请求加上最终回复。记录器会校验每次请求都是上一次的“只追加”扩展，否则报错。
- **理由**：
  - 钩子挂在上游已经在调用的接口上，上游循环本身不需要任何改动。
  - 对齐时逐项检查工具名、轮次和数量，上游行为一变，记录器会直接报错，而不是悄悄产出错位的轨迹。
  - 只追加的前提下，最后一次请求就包含了全部历史，没必要每步重复保存。
- **代价与局限**：
  - 阶段 5e 如果压缩历史，“只追加”就不成立了，记录器会报错。到时需要改成按调用保存请求（存储量约为现在的 n 倍），或者只保存每次请求相对上一次的变化。
  - 轨迹在结果写入之前落盘。如果两次写入之间崩溃，这道题续跑时会再记一条；加载时按题号取最后一条。
  - 工具耗时只包括工具本身，不包括上游循环里的其他开销（可忽略）。
  - 每 100 题的轨迹文件约 4–8 MB，和其他运行结果一样不进版本库。

## D20. 记录器之前的运行：按需转换，但不重建 messages

- **背景**：验收标准要求能回放阶段 1 的任意一道题，而阶段 0/1 的运行没有 `trajectories.jsonl`。
- **备选方案**：
  1. 用新记录器把阶段 1 的 6 个变体全部重跑一遍：约 33 元；
  2. 从 `predictions.jsonl` 按需转换；
  3. 转换，并且把 messages 也近似拼出来（系统提示词、问题、工具调用和结果都有）。
- **最终选择**：方案 2。
  - 转换出的轨迹标记为 `source="converted"`：保留上游记录的工具调用、参数、结果、答案和花费。
  - 每次调用的 token、模型的思考文本、messages 留空，页面上会提示这一点。
  - 另外只用新记录器重跑一次 Full（MuSiQue-100，约 6.4 元），给阶段 4 的上下文增长分析提供完整数据。
- **理由**：
  - 不选方案 3：拼出来的 messages 缺少模型的思考文本和 `tool_call_id`，和真实请求不一致。一旦混进 SFT 数据，就再也分不出来。
  - 阶段 4 需要的“每轮输入 token”只有真实记录才有，重跑一次 Full 就够了，不需要重跑全部变体。
  - 重跑出来的这次 Full 还是同一配置的第三次运行，可以用来改进 D17 中重跑噪声的估计。
- **代价与局限**：阶段 1 的消融变体只能看转换后的轨迹，没有逐步 token。

## D21. 失败标签：独立的 labels.json，分类表放 YAML

- **背景**：回放页面要能给失败案例打标签，标签写回文件；方案里的标签体系是初版，后续会调整。
- **最终选择**：
  - 标签存放在运行目录下的 `labels.json`，按题号保存标签、备注和时间。写入时先写临时文件再改名，避免写到一半崩溃留下损坏的文件。轨迹文件本身从不改写。
  - 分类表放在 `configs/bad_case_tags.yaml`。文件里存的是标签 id，中文名称和说明可以随时修改，但 id 一旦用过就不能改。
  - 在方案的 7 类之外，加了两类：“裁判误判或标准答案有问题”（阶段 0 的裁判核查中出现过）、“API 报错或内容审核拦截”（D16）。否则这些题只能被硬塞进不合适的类别。
  - 页面会显示启发式的“建议标签”，只作参考，不会自动保存。依据包括：是否跑满轮数、是否报错、是否有重复检索或重复读取，以及标准答案字符串有没有出现在工具结果里。
- **理由**：标签是人工判断，和机器产出的轨迹分开存，标错了也不会损坏数据，删掉 `labels.json` 就能从头再标。分类表放在配置文件里，阶段 4 调整分类时不用改代码。
- **代价与局限**：
  - 只适合单人标注：同时打开两个页面编辑同一道题，后保存的会覆盖先保存的。
  - “标准答案是否出现在工具结果里”是字符串匹配，换一种说法的证据会被漏掉，所以这些建议只能作为参考。

## D22. 场景：TiDB 数据库运维诊断（2026-11-03 确认）

- **背景**：阶段 0–2 在 MuSiQue 上复现并评测了 A-RAG，得到了检索引擎选型的依据：A-RAG (Full) 比普通 RAG 准确率高 25 个百分点（p < 0.001），分层的工具接口约省一半成本。下一步要把它放进一个真实场景，做成完整的 Agent。这个场景需要满足四个条件：
  - 有真实的产品和公开文档；
  - 任务能容忍 A-RAG 多轮检索的延迟；
  - Agent 除了查文档，还能操作真实系统；
  - 评测数据能可靠地构造。

  其中延迟是硬约束。阶段 1–2 在 MuSiQue 上的实测（同一配置，5 并发）：

  | 通道 | 延迟 P50 | 延迟 P95 |
  | --- | --- | --- |
  | 普通 RAG（阶段 1） | 4.3 秒 | 20.9 秒 |
  | A-RAG (Full)，阶段 0 / 1 / 2 三次运行 | 40.5 / 28.8 / 40.2 秒 | 106.3 / 75.6 / 106.0 秒 |

  A-RAG 回答一个问题要半分钟以上，只适合用户愿意等待的任务。
- **备选方案**：
  1. **纯文档问答助手**：只检索文档回答问题。用户通常期待几秒内得到答案，A-RAG 的延迟难以接受；大多数问题一次检索就能回答，A-RAG 的优势发挥不出来。评测题只能由 LLM 根据文档生成，标准答案的可靠性要靠大量人工审核。
  2. **TiDB 运维诊断助手**：面向 TiDB 的 DBA 和开发者，同时查文档和查本地集群。
- **最终选择**：方案 2。
  - 语料是 `pingcap/docs-cn` 中与 TiDB 核心相关的子集。release-8.5 分支作为当前版本；release-8.1 分支作为旧版本，用于验证增量索引和构造版本对比题。
  - 本地用 `tiup playground` 启动 v8.5 集群。
  - 主 Agent 用 LangGraph 编排，A-RAG 作为深度检索子 Agent，普通 RAG 作为快速通道。
- **理由**：
  1. **真实的企业产品**：TiDB 是 PingCAP（平凯星辰）的开源分布式数据库，有完整的中文官方文档（CC BY-SA 3.0），不需要虚构公司或数据。
  2. **诊断任务能容忍 A-RAG 的延迟**：排查“查询突然变慢”这类问题，用户本来就要花几分钟甚至几小时，几十秒的等待可以接受。简单的参数查询走普通 RAG 的快速通道（P50 4.3 秒）。两条通道正好对应阶段 1 测出的“准确率高但慢”和“快但准确率低”。
  3. **能接入真实系统**：`tiup playground` 能在本地启动最小集群。Agent 可以查询慢查询、执行计划、系统变量等真实状态，再结合文档给出原因和建议；涉及写操作时必须由用户确认。这样做出来的是完整的 Agent，而不只是问答机器人。
  4. **评测数据可以从结构化来源按规则抽取**：
     - 系统变量文档里，每个变量都有固定格式的作用域、类型、默认值；
     - 发布说明的兼容性变更是固定列的表格；
     - 故障场景可以人为注入，根因是确定的。

     标准答案直接取自原文，不依赖 LLM 出题。LLM 只用于改写问法，改写结果要经过预审和人工复核。
- **代价与局限**：
  - 文档是中文，上游的切句正则只识别英文标点，需要在包装层适配。
  - 本地集群和嵌入模型同时运行时，7 GB 内存比较紧张，需要实测内存峰值并安排运行顺序。
  - “A-RAG 优于普通 RAG”是在英文多跳问答上得到的结论，在中文运维文档上是否成立，要在阶段 4 用新评测集重新验证。
  - 故障是人为注入的，比真实生产环境中的问题简单。

## D23. 答案引用：从答案里解析块编号，不改提示词

- **背景**：方案要求最终答案标注依据的文档和段落。上游系统提示词本来就要求“引用支持答案的具体块”，阶段 2 的 100 个答案里有 97 个写了“Chunk N”。
- **备选方案**：
  1. 修改提示词，要求按固定格式输出引用（例如 JSON）。
  2. 不改提示词，事后从答案中解析块编号，再映射到块元数据里的文档路径和标题路径。
- **最终选择**：方案 2（`research_agent/eval/citations.py`）。每条引用还会对照轨迹标出状态：
  - 读过全文（read_chunk、整块返回的检索、普通 RAG 放进提示词的块）；
  - 只看过检索片段；
  - 从未出现过（编造的编号）；
  - 不存在。

  运行器把引用写进每条预测记录，回放页面显示在答案下方，运行摘要和对比表统计以下几项：
  - 带引用的答案比例；
  - 引用中读过全文的比例；
  - 从未出现的引用数；
  - 评测集带标准证据块时，“引用了标准证据块”的答案比例。
- **理由**：改提示词会让 A-RAG (Full) 和论文设置不一致，结果就不能和基准子集直接对照。现有答案已经自带引用，解析就够用。
- **验证**（在已有的 MuSiQue 运行上离线计算，不花钱）：

  | 运行 | 带引用的答案 | 引用中读过全文 | 从未出现的引用 |
  | --- | --- | --- | --- |
  | Full（阶段 2） | 97% | 85% | 0 |
  | w/o read_chunk（阶段 1） | 92% | 100% | 0 |
  | 普通 RAG（阶段 1） | 35% | 100% | 0 |

  普通 RAG 的提示词里没有要求引用，它的块编号只出现在上下文的块标题中。阶段 1 全部变体的引用统计见 `docs/results/stage1_musique100_comparison.md`。
- **代价与局限**：
  - 只识别“chunk N”这类写法。
  - 只检查被引用的块有没有被看过，不检查它是否真的支持答案；评测集带标准证据块时，用“是否引用了标准证据块”部分弥补。
  - MuSiQue 的块没有文档和标题元数据，引用只能显示块编号。自建语料的块带有文档路径和标题路径（`research_agent/ingest`）。

## D24. 索引向量用 float32 编码

- **背景**：上游 `scripts/build_index.py` 用 Qwen3-Embedding 的默认精度 bf16 编码。增量索引只为新出现的文本编码，其余沿用上一次的向量；要让增量构建和全量构建等价，同一句话不管和哪些句子一起编码，向量都必须一样。
- **实测**（MuSiQue 语料的前 3,000 句，其中 2,732 句互不相同；RTX 3060 Laptop，批大小 16。查询是 MuSiQue 100 题子集的前 20 题，查询向量按上游的方式用 bf16 编码）：

  | | bf16 | fp32 |
  | --- | --- | --- |
  | 同一批输入重复编码 | 完全一致 | 完全一致 |
  | 打乱顺序（同一句话分到不同批次）后的最大偏差 | 5.4e-3 | 4.9e-7 |
  | 批大小 16 和 32 的最大偏差 | 6.1e-3 | 8.5e-7 |
  | 20 个查询中，两种批次组合下前 5 个结果完全相同（按句子文本比较） | 18 / 20 | 20 / 20 |
  | 编码 3,000 句的耗时 | 12.0 秒 | 25.2 秒 |

  - 在 bf16 下，一句话的向量取决于和它分在同一批的其他句子：补齐长度不同，计算顺序也就不同。这个偏差足以改变检索排序，上游脚本自己重建一次索引也会这样。
  - fp32 下，如果按句子编号比较前 5 个结果，有 4 个查询不一样，但全部是重复句子之间的并列：同一句话出现在多个段落里，相似度完全相同，而上游的 `argsort` 不是稳定排序。
- **备选方案**：
  1. 保持 bf16，增量构建只保证文本一致。
  2. 索引向量用 fp32。
  3. 不做增量，每次全量重建。
- **最终选择**：方案 2。`CorpusConfig.embedding_dtype` 默认是 `float32`（`research_agent/ingest/index.py` 的 `SentenceTransformerEmbedder`）。查询端保持上游默认，不做改动。
- **理由**：只有在 fp32 下，“沿用旧向量”才和“重新编码”等价，增量构建的正确性才能用逐块比较来验证。全量重建的耗时随语料线性增长，而文档更新通常只改动少数文件。
- **代价与局限**：
  - 编码耗时约为 bf16 的 2 倍。
  - 查询向量仍是 bf16，和索引向量精度不同。20 个查询的 bf16 与 fp32 向量余弦相似度最低 0.998。这是固定偏差，同一个查询每次得到同样的向量，不影响检索结果的可复现性，但两边严格来说不对称。是否把查询端也改成 fp32，可以和其他检索改进一起评估。
  - MuSiQue 的现有索引是上游脚本用 bf16 建的，同样有批次依赖：只要不重建就能复现，一旦重建，检索结果可能变化。阶段 0–2 的结果都基于这份索引。

## D25. TiDB 语料：从 git 分支读取核心子集，按标题切块并合并到 1,000 token

- **背景**：语料范围已在方案中确认：`pingcap/docs-cn` 的 TiDB 核心子集，以 release-8.5 为当前版本，release-8.1 为旧版本。上游 A-RAG 直接使用数据集自带的块（MuSiQue 每块中位数约 1,150 token），技术文档需要自己切块，并在每个块上保留来源文件和标题路径，供答案引用使用（D23）。
- **读取方式**：
  - 不检出（checkout）分支，而是从 git 对象直接读取指定提交下的文件（`research_agent/ingest/sources.py` 的 `GitSource`）。两个版本可以并排读取，增量索引的验证不需要来回切换分支。
  - docs-cn 有 2,800 多个文件和很长的历史。`fetch` 只拉取两个分支各自最新的一个提交，并且不下载文件内容（`--depth 1 --filter=blob:none`），读到哪个文件才下载哪个。两个版本都读过之后，克隆目录约 1 MB。
- **子集**（`configs/corpora/tidb_docs.yaml`）：方案清单中的 58 个文件里，`memory-control.md` 在 release-8.5 上不存在，对应的文档是 `configure-memory-usage.md`（TiDB 内存控制）；`explain-mpp.md` 讲的是 TiFlash 的 MPP 模式，按排除规则不收。另外补充了 7 个和故障场景直接相关的文件：`statistics.md`、乐观和悲观事务两篇，以及 `information_schema` 下慢查询、锁等待、事务、死锁四张系统表的文档。共 65 篇，原文 56.0 万 token，清洗后 45.4 万 token（D27）。release-8.1 上同样的路径有 52 篇（没有 v8.2 及之后的发布说明和 `tidb-performance-tuning-config.md`）。
- **切块的备选方案**（8.5 子集实测，token 按 tiktoken o200k 计）：

  | 方案 | 块数 | 中位数（token） | 不到 100 token 的块 | 从 8.1 到 8.5 后文本变了的块 |
  | --- | ---: | ---: | --- | --- |
  | 每个标题段落单独成块 | 2,140 | 147 | 30% | 26% |
  | 同一文档内合并到 500 token | 1,175 | 449 | 2% | 47% |
  | **同一文档内合并到 1,000 token** | **574** | **919** | **1%** | **59%** |
  | 同一文档内合并到 2,000 token | 291 | 1,815 | 1% | 67% |

- **最终选择**：同一文档内合并到 1,000 token（`research_agent/ingest/chunker.py`）。
  - 先在代码块之外的每个标题处切开，每段记住自己的标题路径，再在同一文档内贪心合并。
  - 超长的段落按空行切分；单个超长块中，表格按行切并在每块重复表头，代码块按行切并重新补上代码围栏，纯文本先按句子切、再按词切。
  - 每个块的第一行是来源行：`[文档路径]` 加上块内**所有段落**的标题路径（2026-11-03 修订，见下文“来源行”）。
  - 块编号是“按文档路径排序后的位置”，和基准数据集的格式一样。
- **理由**：
  - 块的大小接近 MuSiQue，每次读取返回的长度和花费与阶段 0–2 可比；上游 `read_chunk` 的工具描述也是按这种大小写的。
  - 每个标题段落单独成块时，参数文档里每个变量一块，三成的块不到 100 token，检索结果会非常碎，Agent 要多读很多次。
  - 来源行让模型不查元数据就知道这段文字出自哪个文档、哪个变量，也能据此引用；关键词检索还能匹配到标题。
- **代价与局限**：
  - 合并得越大，文档里改一处就越容易让后面的切块边界整体后移：8.1 到 8.5，574 个块中有 59% 的文本变了，只按段落切时是 26%。增量构建仍然只为新文本编码（D26），但块编号在版本之间不稳定。评测集因此同时保存证据的文档路径和原文引用，换版本后可以重新定位（`research_agent/evalset/dataset.py` 的 `Evidence`）。
  - 来源行使每个块平均多出约 56 token（中位数 38），约占块长度的 6%。

### 来源行：列出块内全部段落（2026-11-03 修订）

- **问题**：最初的来源行只写块里第一个段落的标题路径。阶段 3 验收时，v8.5.0 发布说明的块 243 从“功能详情 › 安全”一直延续到“兼容性变更 › 系统变量”，答案在最后一个标题下，但来源行和引用都只显示“安全”，A-RAG 没有读这个块，答错了版本题。
- **备选方案**：
  1. 不跨二级标题合并：发布说明的“兼容性变更”会另起一块。但 `system-variables.md` 的 490 个变量都是同一个二级标题下的三级标题，一个块里仍然有好几个变量，来源行还是只能显示第一个，修不好这类文档。
  2. 来源行列出块内所有段落的标题路径，相同的上级标题只写一次。
- **最终选择**：方案 2（`research_agent/ingest/chunker.py` 的 `merge_heading_paths`）。
  - 块的元数据 `sections` 保存块内全部段落的标题路径；`headings` 仍是第一个段落的路径，保持兼容。
  - 合并规则：先去掉“是另一条路径前缀”的路径（例如只有引言的“兼容性变更”，它已经隐含在“兼容性变更 › 系统变量”里）；所有路径共同的前缀写一次；剩下的按上级标题分组，同一上级下的段落用“、”连接，不同组之间用“；”分隔。例如块 243：`[releases/release-8.5.0.md] TiDB 8.5.0 Release Notes > 功能详情 > 安全；兼容性变更 > 行为变更、系统变量`。
  - **截断**：整行超过 150 token（`max_header_tokens`）时，从后往前去掉段落，直到放得下，末尾写“等 N 个段落”，至少保留第一个段落。正文里的标题都还在，只是来源行不再列出全部。
  - 引用解析用同样的规则显示块内全部段落（`research_agent/eval/citations.py`）。
  - 切块边界不变（`max_tokens` 只计正文），块编号和块的划分都与修订前相同。
- **实测**（8.5 子集，574 个块）：

  | | 修订前（只写第一个段落） | 修订后 |
  | --- | ---: | ---: |
  | 来源行长度：平均 / 中位数 / P90 / 最长（token） | 28.2 / 29 / 38 / 65 | 55.7 / 38 / 124 / 150 |
  | 被截断的块 | — | 30（全部在系统变量和三个配置文件文档里） |
  | 每块平均段落数 | — | 3.7（最多 20） |

  修订后重跑阶段 3 的验收：A-RAG 的版本题答对了，引用块 243。它先读了配置参数的块 244，再搜关键词“兼容性变更”时，keyword_search 的片段里出现了来源行的“兼容性变更 > 行为变更、系统变量”，于是读了块 243（experiments.md 阶段 3 一节）。只跑了一次，不能排除重跑本身的随机性。
- **代价与局限**：
  - 来源行平均长了约 28 token，读一个块多花约 3% 的 token。
  - 参数文档的来源行是一长串变量名，加上每个变量的“从 vX 版本开始引入”。被截断的 30 个块里，排在后面的变量不出现在来源行中。
  - 合并后的写法有一点歧义：“；”之后的部分是相对于共同前缀的路径，不是相对于前一组。

## D26. 增量索引：上一次构建就是缓存，用 8.1 → 8.5 验证与全量构建等价

- **背景**：文档会随版本更新，方案要求文档增删改时只重建受影响的部分。上游 `scripts/build_index.py` 每次都对所有句子重新编码。
- **最终选择**（`research_agent/ingest/index.py`）：
  - **输出格式与上游完全一致**：`chunks.json`（dict 列表，上游工具原样接受、忽略多出的字段）、`index/sentence_index.pkl`（与上游脚本写出的字段相同）、普通 RAG 的块级向量缓存（D10）。上游的三个检索工具直接读取构建目录。
  - **按“清洗后的文档内容”算哈希**：哈希不变的文档直接沿用上次的块，不重新切块。
  - **向量按文本复用**：上一次构建里已有向量的句子和块直接沿用，只有新出现的文本才送进模型编码。
  - **写入顺序**：先写所有数据文件，最后写 `manifest.json`。如果中途崩溃，manifest 记录的 chunks 哈希和实际文件对不上，下次构建会自动退回全量构建。
  - **配置变更时缩小复用范围**：切块配置变了，就重新切所有文档，但句子向量照样复用；嵌入模型、向量精度或切句方式变了，就不复用向量。
  - 索引向量用 fp32 编码（D24），否则增量构建和全量构建的向量不一致。
  - 构建报告记录耗时、编码量，以及进程内存和显存的峰值。
- **验证**（`python -m research_agent.ingest build` 和 `compare`，本地 RTX 3060 Laptop 6 GB，WSL2 7.6 GB 内存）：先全量构建 release-8.1，再在同一目录增量更新到 release-8.5，与独立的 release-8.5 全量构建逐块比较：
  - **块文本和句子完全一致**，向量最大偏差：句子 8.4e-7，块 6.4e-7；
  - 两版之间：新增 13 篇（12 篇发布说明和 `tidb-performance-tuning-config.md`），修改 34 篇，删除 0 篇，未变 18 篇。

  | 构建 | 耗时 | 编码的句子 | 复用的句子向量 | 编码的块 | 复用的块向量 | 内存峰值 | 显存峰值（分配 / 预留） |
  | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
  | 8.1 全量 | 190 秒 | 12,677 | 0 | 427 | 0 | 4.1 GiB | 2.7 / 3.1 GiB |
  | 8.1 → 8.5 增量 | 108 秒 | 3,925 | 17,048 | 339 | 235 | 4.1 GiB | 2.5 / 3.1 GiB |
  | 8.5 全量 | 254 秒 | 16,038 | 0 | 574 | 0 | 4.1 GiB | 2.7 / 3.1 GiB |

  表中是来源行修订、块向量批大小改为 4 之后的结果（块文本和句子与全量构建完全一致，向量最大偏差：句子 7.7e-7，块 7.9e-7）。修订前的第一次验证同样等价（偏差 8.4e-7 / 6.4e-7）。增量构建用时是全量的 43%。
- **块向量的批大小**（2026-11-03 修订）：第一次验证时句子和块都按 16 个一批编码，显存预留峰值 5.7 GiB，接近 6 GB 的上限。1,000 token 的整块占用的激活显存远大于句子，所以块向量单独设批大小（`CorpusConfig.chunk_batch_size`），默认 4。在 128 个块上（含最长的 32 个）单独测：

  | 块向量批大小 | 每块耗时 | 显存分配 / 预留峰值 |
  | ---: | ---: | --- |
  | 16 | 257 毫秒 | 3.42 / 4.65 GiB |
  | 8 | 242 毫秒 | 2.83 / 3.56 GiB |
  | **4** | **227 毫秒** | **2.54 / 3.05 GiB** |
  | 2 | 222 毫秒 | 2.69 / 3.21 GiB |

  批越小反而越快：块的长短不一，批越大，补齐到批内最长块的浪费越多。调整前后的完整构建（构建报告记录了两种批大小）：

  | 构建 | 批大小 16（调整前） | 批大小 4（调整后） |
  | --- | --- | --- |
  | 8.1 全量：总耗时 / 块编码 | 223 / 127 秒 | 190 / 94 秒 |
  | 8.1 → 8.5 增量：总耗时 / 块编码 | 107 / 76 秒 | 108 / 75 秒 |
  | 8.5 全量：总耗时 / 块编码 | 268 / 143 秒 | 254 / 129 秒 |
  | 显存预留峰值 | 5.7 GiB | 3.1 GiB |

  调整后的块文本多了来源行（平均长约 28 token），所以两列的块编码时间不是严格同条件的比较；但显存峰值的下降与上表一致。fp32 下批大小对向量的影响在 1e-6 以下，旧向量可以继续复用。
- **理由**：不需要额外的缓存目录或数据库，构建目录本身就是缓存，而且上游工具可以直接读取。复用以“文本”为键，与文档是否改动无关，所以文档里只改了一处时，没有变化的块和句子也会被复用。
- **代价与局限**：
  - 块编号是位置编号（D25），新增一篇文档会让后面所有块的编号顺移。
  - 上一次构建的整个句子索引都要读进内存（8.5 约 2.1 万句、90 MB）。
  - **内存比较紧**：内存峰值 4.1 GiB 主要来自加载 fp32 的嵌入模型和 CUDA 运行库，建索引时不要同时运行本地 TiDB 集群。显存预留峰值调整后为 3.1 GiB。

## D27. Markdown 清洗：只保留读者看到的文字，链接只保留文字

- **背景**：docs-cn 的 Markdown 是给文档站渲染用的，里面有很多不是正文的标记。在 8.5 子集（65 篇）里实测：
  - 每篇都有 YAML 头信息（标题、摘要）；
  - Hugo 短代码 `{{< copyable "sql" >}}` 137 处，分布在 18 篇里，渲染后是代码块上的“复制”按钮；
  - HTML 注释 189 处（6 篇），有些是被注释掉的旧内容，例如 `<!-- - TiDB Cloud 中，从 v6.5.0 开始…-->`；
  - 版本标记 `<span class="version-mark">从 v6.1.0 版本开始引入</span>` 525 处，主要在参数文档的标题里；
  - 发布说明的“功能详情”是 HTML 表格（6 篇，带 `rowspan`），Markdown 表格的单元格里也有 `<ul><li>` 列表；
  - 站点组件 `<EmailSubscriptionWrapper />`；
  - 链接 5,813 个，链接地址占原文 token 的 **15.2%**（56.0 万中的 8.5 万）。发布说明里每条修复都带 issue 和作者链接，参数文档的锚点里还有中文（`#tidb_mem_oom_action-从-v610-版本开始引入`）。
- **备选方案**：
  1. 原样入库：最简单，但标记会进入块文本、检索片段和 token 计数。
  2. 渲染成 HTML 再提取文字：最忠实，但要实现 Hugo 短代码和站点组件的渲染，成本高。
  3. 针对实际出现的写法逐条清洗，代码块里的内容一律不动。
- **最终选择**：方案 3（`research_agent/ingest/markdown.py` 的 `normalize_markdown`）：
  - 删除：HTML 注释、Hugo 短代码、驼峰命名的站点组件标签；
  - HTML 表格：每行转成一行文字，单元格用 ` | ` 连接，行与行之间空一行，方便切块器在行边界切开；单元格里的列表项用“；”连接；
  - Markdown 表格单元格里的 `<ul><li>` 列表同样用“；”连接；
  - 版式标签（`span`、`a`、`p`、`div` 等）去掉标签、保留中间的文字，所以版本标记“从 v6.1.0 版本开始引入”留在标题里；`<code>` 换成反引号；图片保留替代文字；
  - 链接只保留文字（`loader.link_targets: false`）；
  - 不认识的标签（例如 `<host>:<port>` 这种占位符）不动。
- **效果**：65 篇文档从 56.0 万 token 降到 45.4 万（−19%），其中链接地址约 8.5 万。清洗后检查：除了一处在代码块里的链接（TOML 配置的注释，按规则不动），没有残留的表格标签、短代码、组件标签或链接地址。
- **理由**：
  - 块的 token 少了约五分之一，同样的上下文预算能多读约 20% 的正文。
  - Agent 只能按块编号读取，没法点开链接，链接地址对它没有用。链接文字（例如被链接的变量名）都保留了。
  - 发布说明的表格转成按行的文字后，模型能读懂；保留 HTML 标签的话，一个单元格的内容会被 `<td>`、`<li>` 打散。
- **代价与局限**：
  - 链接表达的“这个变量的详细说明在另一篇文档”的关系丢了。如果以后需要沿链接扩展检索，要从原文重新提取。
  - HTML 表格的 `rowspan` 没有展开：合并单元格只出现在第一行，后面几行少了“分类”这一列。
  - 规则是针对 docs-cn 实际出现的写法写的，换别的文档站需要重新检查。
  - 头信息里的 `summary`（一句话摘要）没有放进正文，只用 `title` 作为文档标题。
  - **修复过的问题**（2026-11-03，阶段 4 抽取发布说明时发现）：最初只要一行里出现 `<table` 就当作 HTML 表格的开始。v8.5.6 发布说明正文里的行内代码 `` `SELECT ... FOR UPDATE OF <table>` `` 被当成了表格，后面的内容（包括整个兼容性变更）全被吞掉，15,552 个字符只剩 1,511。现在表格必须从行首开始，并且后文有 `</table>`，否则原样保留。65 篇中只有这一篇受影响。修复后增量更新只重新处理了这一篇：新增 6 个块、103 句，用时 2.8 秒；与全量构建等价（块数 574 → 579）。

## D28. 中文切句：中文句末标点切开，英文句号只在后面跟空白时切

- **背景**：semantic_search 检索的是句子：建索引时把每个块切成句子并编码，查询时找最相似的句子，再返回所在的块和这些句子。keyword_search 返回的片段也是“块里包含关键词的句子”。上游的切句规则是在 `.`、`!`、`?` 和换行处切开，建索引时还会丢掉 10 个字符及以下的句子。这在中文技术文档上有两个问题：
  - 中文的“。！？；”不切，一整段话就是一个“句子”；
  - 每个 `.` 都切，`v8.5.0` 被切成 `v8`、`5`、`0`，`1.5` 丢了小数，切出来的碎片又因为太短被丢掉。
- **实测**（8.5 子集，574 个块）：

  | | 上游规则 | 新规则 |
  | --- | ---: | ---: |
  | 句子数 | 19,385 | 21,111 |
  | 句子长度中位数 / P90（字符） | 37 / 111 | 36 / 101 |
  | 以 `v8`、`v7`、`v6` 结尾的断句 | 930 | 0 |
  | keyword_search 每次返回的 token（8 组中文和参数名关键词的平均） | 704 | 586（−17%） |

  例如“从 v8.5.0 开始，该变量默认值从 `1.5` 改为 `2.0`。修改后需要重启才能生效！”，上游切成“0 开始，该变量默认值从 `1`”和“0`。修改后需要重启才能生效！…”，新规则切成“从 v8.5.0 开始，该变量默认值从 `1.5` 改为 `2.0`”和“修改后需要重启才能生效”。用关键词 `v8.5` 搜索时，上游规则下这个块的片段里一句匹配都没有（“no exact sentence match”）。
- **备选方案**：
  1. 保持上游规则。
  2. 只增加中文标点。
  3. 增加中文标点，并且英文的 `.!?` 只在后面跟空白或文本结尾时才切。
  4. 用分词工具（例如 jieba）或 NLP 句子切分器。
- **最终选择**：方案 3（`research_agent/ingest/sentences.py`）。
  - 在“。！？；”处切开；英文的 `.!?` 只在后面跟空白或文本结尾时切；换行照样切。
  - 最短长度沿用上游的“超过 10”，但一个汉字按 2 计：一个汉字的信息量大约相当于一个英文单词，而不是一个字母。这样“单条查询内存上限”（8 个字）会保留，“默认值：0”这种几乎每个参数都有的短行会去掉。
  - 建索引时由语料配置的 `sentence_split: multilingual` 打开，manifest 记录所用的切句函数，换了切句函数会被检测到。
  - keyword_search 的片段由运行配置的 `data.sentence_split: multilingual` 打开：在我们创建的工具实例上替换切句方法，不改上游文件。片段不设最短长度，和上游一致。
  - 默认值仍是 `upstream`，MuSiQue 的索引和运行不受影响。
- **理由**：
  - 方案 2 解决不了版本号和小数被切断的问题，而 TiDB 文档里到处是版本号（“从 v6.1.0 版本开始引入”）。
  - 方案 4 要引入新依赖，句子边界本来就由标点决定，规则足够。
- **代价与局限**：
  - `e.g. `、`etc. ` 这类后面跟空格的缩写仍会被切开，和上游一样。
  - 英文分号不切（上游也不切）；中文分号切，因为中文文档常用分号分隔并列的完整句子。
  - 句子数比上游多 9%，句子向量的编码时间相应增加。

## D29. 普通 RAG 可以要求引用块编号（默认关闭）

- **背景**：阶段 3 的验收要求普通 RAG 和 A-RAG 都能给出正确的引用。普通 RAG 的提示词按论文 Figure 6（D10），只要求“根据上下文直接回答”，答案里不会写块编号。MuSiQue 上 35% 的答案带编号，只是因为上下文里的块标题是 `[Chunk id]`，模型偶尔顺手写上。在 TiDB 验收的 2 道题上，普通 RAG 的答案一个块编号都没写，尽管它检索到的第一名正是标准证据块。
- **备选方案**：
  1. 不改提示词，把检索到的前 5 个块当作来源展示。但这些块不一定都支持答案，也就无法和 A-RAG 的引用率比较。
  2. 改提示词，要求按固定格式引用。
  3. 加一个开关，打开时在用户消息末尾加上 A-RAG 系统提示词里的那一句“Cite the specific chunks that support your answer”。
- **最终选择**：方案 3（`naive_rag.cite_chunks`，`research_agent/baselines/naive_rag.py` 的 `CITE_INSTRUCTION`），默认关闭。
- **理由**：
  - 默认关闭，阶段 1 的 MuSiQue 结果仍然可以按原样复现。
  - 引用要求的措辞与 A-RAG 相同，打开后两个通道在“要求引用”这一点上是对称的，引用率才有可比性。
  - 对比表的可比性检查允许 `naive_rag.*` 不同，并会在表下列出这一项差异。
- **验证**（TiDB 验收的 2 道题）：打开后带引用的答案从 0% 变为 100%，参数题引用块 403，解析为 `system-variables.md › 系统变量 › 变量参考 › tidb_mem_quota_query`，正确；两题的对错不变。
- **阶段 4 起的用法**（2026-11-03 确认）：
  - 阶段 4 的基线对比中，普通 RAG 打开 `naive_rag.cite_chunks`，两个通道都被要求引用，引用率可以直接比较。
  - 快通道在产品中也必须给出引用：用户需要知道答案依据的是哪篇文档、哪一节，不能只给结论。
- **代价与局限**：打开后提示词与论文不同，阶段 4 的普通 RAG 结果不能直接和阶段 1 MuSiQue 上的普通 RAG 行对照（那一行没有要求引用）。

  - 改写模型是 qwen3.7-flash，与被测 Agent（qwen3.7-plus）、预审和裁判（qwen-plus-2025-12-01）都不同，避免同一个模型既出题又把关。
  - 改写时给模型参数说明的全部条目（最多 400 字）；规则检查：不能出现参数名或它的最后一段，不能出现答案，必须是问句、不超过 80 字；不通过时把原因反馈给模型改写一次。说明太笼统时模型可以放弃。

- **版本变更题**：
  - **比较两个具体版本**：v8.1.0 和 v8.5.8。v8.5.8 是 docs-cn release-8.5 分支收录的最新补丁版本，也是 tiup 镜像上 linux/amd64 可用的最新 v8.5 版本（2026-11-03 查询），阶段 5 的本地集群也锁定这个版本。
  - **问法**：
    - 修改：“与 v8.1.0 相比，v8.5.8 中……的默认值有什么变化？”答案写明哪个版本改的，例如“从 1 改为 MAX(1, MIN(4, CPU 核数 / 8))（v8.5.4 起）”。不问“升级后怎么变”，因为有的变更写明了“升级的集群保持原值”。
    - 新增 / 废弃 / 删除：“……是在 TiDB 哪个版本新增（废弃、删除）的？”

    - 修改：发布说明里的旧值必须等于 release-8.1 文档的默认值，新值必须等于 release-8.5 文档的默认值；v8.1.1 和 v8.1.2 也改过这个参数的题丢弃（本次没有）。
    - 新增、废弃：发布说明的版本必须出现在参数文档的版本标记里（“从 vX 版本开始引入”“从 vX 开始，该配置项被废弃”）。标记里有多个版本时（多条版本线同时引入，例如“从 v7.5.7 和 v8.5.4 版本开始引入”），问法限定为“在 v8 系列中”，标记里所有 v8 版本都是可接受的答案。
    - 删除：参数在 release-8.1 文档里有、在 release-8.5 文档里没有。
    - 参数文档里找不到、或名称对应多个参数的，无法核对，一律丢弃。

## D31. 主 Agent：一张 LangGraph 图，A-RAG 整体当作一个工具，修改用 interrupt 等确认

- **背景**：阶段 6 要把文档检索、集群诊断、修改确认和多轮对话串成一个助手。A-RAG 本身就是一个完整的检索 Agent，诊断还需要集群工具和人工确认。
- **备选方案**：
  1. 把集群工具加进 A-RAG 的工具集，一个 Agent 做所有事。
  2. 一张图：分类后分别进入文档检索和诊断循环，A-RAG 原样保留，作为诊断循环里的一个工具（`search_docs`）。
  3. 多 Agent 协作（检索 Agent、诊断 Agent 互相交接）。
- **最终选择**：方案 2（`research_agent/assistant/graph.py`，架构见 docs/architecture.md）。
  - 节点：condense → route →（retrieve | diagnose ⇄ confirm | refuse）→ check。
  - 修改只能经 `propose_*` 生成待确认项，`confirm` 节点用 `interrupt()` 暂停整张图，`Command(resume=…)` 恢复；会话和待确认项存在 SQLite 检查点里。
  - `check` 节点：答案背后没有证据（被读过或看过片段的引用块、集群工具结果）就拒答。诊断时集群连不上，单独说明，不让模型猜原因。
- **理由**：
  - A-RAG 的提示词和工具不变，阶段 4 的评测结果对助手里的文档检索仍然有效；方案 1 改了工具集和提示词，等于换了一个 Agent，要重新评测。
  - 分类节点是阶段 7 分流的落点：`Services.choose_channel(question, intent)` 决定走 A-RAG 还是快通道，不用改图。
  - `interrupt()` 让“确认”成为图的一部分：确认前什么都不执行，跨请求、跨进程重启都能恢复，阶段 9 的 HTTP 接口只要把确认请求转成 `resume`。
  - 方案 3 对这几类问题没有必要，交接也更难测试。
- **代价与局限**：
  - 每轮多两次小模型调用（改写、分类），约 0.0002 元、1–2 秒。
  - 分类错了就走错分支：诊断问题被分成研究问题时不会查集群。没有回退。
  - 诊断循环里调用 `search_docs` 会跑一整次 A-RAG（十几秒到两分钟），是诊断延迟的主要来源。
  - 证据检查只看“有没有”，不看引用是否真的支持答案（演示中参数题答对了，但引用的是不相关的 explain-joins.md）。

## D32. 阶段 7 分类路由：参数查询交给快通道不划算，助手默认全部走 A-RAG（2026-11-03）

- **背景**：阶段 4 的基线显示，快通道（普通 RAG，要求引用）延迟 P50 只有 A-RAG 的 38%，准确率低 16 个百分点。阶段 7 只做分类路由：沿用助手的意图分类器（qwen3.7-flash，`research_agent/assistant/routing.py`），参数查询（param_lookup）交给快通道，其余交给 A-RAG，和“全部 A-RAG”在阶段 4 的 126 题上比较一次。
- **备选方案**：
  1. 全部 A-RAG（阶段 6 的做法）。
  2. 分类路由：param_lookup → 快通道，其余 → A-RAG。
  3. 分类路由加回退：快通道回答“上下文中没有”时再交给 A-RAG。不在阶段 7 的范围内，只用已有结果离线估算，没有实现。
- **结果**（`configs/suites/stage7_routing.yaml`，`docs/results/stage7_routing.md`；同一模型和参数，全部 A-RAG 一行复用阶段 4 的运行）：

  | | 准确率 | 描述问法 | 直接问法 | 版本变更 | 延迟 P50 / P95 | 每 100 题花费 |
  | --- | ---: | ---: | ---: | ---: | ---: | ---: |
  | 全部 A-RAG | 100% | 100% | 100% | 100% | 13.1 / 29.8 s | 1.37 元 |
  | 分类路由（实测） | 85.7% | 70.0% | 88.0% | 100% | 7.3 / 36.3 s | 1.37 元 |
  | 分类路由，按阶段 4 的接口速度（估算） | 85.7% | | | | 7.3 / 31.5 s | 1.37 元 |
  | 分类路由加回退（离线估算，未实现） | 96.0% | | | | 7.5 / 31.5 s | 1.52 元 |

  - 分类器把 90 道参数题全部分为参数查询；36 道版本变更题中 30 道分为研究、6 道分为参数查询（这 6 道快通道都答对了）。分类器每题约 1.9 秒、0.00007 元。
  - 与全部 A-RAG 相比 −14.3 个百分点，95% 置信区间 [−21.5, −8.4]，McNemar p < 0.001（18 题只有 A-RAG 答对，0 题相反）。
  - 快通道答错的 18 题中，13 题回答“上下文中没有相关信息”（稠密检索没取到对应的块），能被识别出来；方案 3 的估算就是把这 13 题换成阶段 4 的 A-RAG 结果。
- **最终选择**：助手默认全部走 A-RAG（`configs/assistant.yaml` 的 `fast_intents: []`）；分类路由保留为配置项，评测方法 `method: routed` 保留。
- **理由**：
  - 准确率损失大且显著，描述问法（不知道参数名时）损失 30 个百分点。运维场景里答错一个默认值的代价，比多等几秒大得多。
  - **没有省钱**：在被分到快通道的 96 题上，快通道每题 0.0108 元，A-RAG 0.0118 元。快通道每次把 5 个整块（约 4,800 token）放进提示，几乎没有缓存；A-RAG 读得少，63% 的输入命中缓存。
  - 只省了延迟：P50 从 13.1 秒降到 7.3 秒；P95 反而变差，因为分类器的约 2 秒加在了最慢的 A-RAG 题上。
- **同时修复：证据检查误拒正确答案**。A-RAG 有 13 个答案（10.3%）没有在回答中写块编号，但这 13 个都是对的，而且都读过标准证据块。助手的证据检查只认回答中引用的块，会把它们全部拒答。现在，A-RAG 的回答没有引用时，用它完整读过的块作为依据，并标注“读过，回答中未标注”（`research_agent/assistant/retrieval.py` 的 `doc_citations`）；用阶段 4 的记录检验，126 题全部通过证据检查。快通道不做这种回退：它的 5 个块都在提示里，并不说明回答用了哪一块。
- **代价与局限**：
  - 只跑了一次。延迟受接口负载影响：同样的题，这次运行两个通道都比阶段 4 慢约 40%（普通 RAG 4.6 → 6.7 秒，含分类 1.9 秒；A-RAG 15.7 → 20.6 秒），所以另给了按阶段 4 速度组合的估算。
  - 裁判把 2 道与标准答案一致的简短回答判错（bad_cases.md 第 2 条）；改判后分类路由为 87.3%，结论不变。
  - 这个评测集上 A-RAG 已经是 100%，快通道的优势只能体现在延迟上；问题更难、A-RAG 循环更长时，结论可能不同。
  - 方案 3 是用阶段 4 的结果拼出来的估算，“没有找到”的识别用的是正则表达式，没有实测。
