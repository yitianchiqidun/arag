# 设计决策记录

格式：背景 → 备选方案 → 最终选择 → 理由 → 代价与局限。按时间顺序追加，编号不复用。

---

## D1. 扩展上游的方式：继承和包装，不改源码

- **背景**：项目要清楚区分“A-RAG 原作者的工作”和“我的工作”，同时要在上游代码之上加计费、计时、轨迹记录等功能。
- **备选方案**：
  1. 直接修改 `src/arag/` 和 `scripts/`；
  2. 继承上游类，在子类里覆盖方法；
  3. 完全重写一套 Agent，只复用工具。
- **最终选择**：方案 2。`MeteredLLMClient(LLMClient)`、`MeteredBatchRunner(BatchRunner)`、`RecordingAgent(BaseAgent)`，上游 `Evaluator` 直接实例化复用。`scripts/` 下的脚本不是包，通过 `importlib` 按文件路径加载（`research_agent/upstream.py`）。
- **理由**：`git diff upstream/main -- src scripts` 为空，边界一目了然；上游的行为（提示词、工具、循环）保持原样，复现结果才有意义；以后合并上游更新时冲突最少。
- **代价与局限**：`MeteredLLMClient.chat` 为了加 `extra_body` 和重试，复制了上游 `chat` 构造请求体的约 10 行代码，上游改这段时需要同步。`BaseAgent.run` 是一个整体方法，没有钩子，以后改循环（规划、记忆）只能整体覆盖 `run`。

## D2. LLM：百炼 Qwen，主实验固定日期快照

- **背景**：方案选定阿里云百炼的 Qwen 系列（与后续 SFT 学生模型同家族）。开工时（2026-10-30）百炼上同时存在 `qwen-plus`（别名，指向 `qwen-plus-2025-12-01`，输入/输出 0.8/2 元每百万 token）和更新一代的 `qwen3.7-plus`（2/8 元）。
- **备选方案**：qwen-flash（最便宜）/ qwen-plus / qwen3.7-plus / qwen3-max（最贵）。
- **最终选择**：主实验用 plus 档，配置里写**日期快照名**而不是别名；调试用 flash 档。两代 plus 都在 MuSiQue-100 上跑了一遍（见 experiments.md）：qwen3.7-plus 的 LLM-Acc 为 68%，qwen-plus-2025-12-01 为 57%（配对检验 p = 0.035）；每 100 题花费分别为 6.2 元和 2.2 元。**2026-10-30 确定主模型为 `qwen3.7-plus-2026-05-26`**（主配置 `configs/musique_qwen37_plus.yaml`），阶段 1 起所有对比表都用它；`qwen-plus-2025-12-01` 只保留为裁判。
- **理由**：
  - 多跳问答需要较强的推理和工具调用能力，flash 档太弱，A-RAG 与基线的差距可能被噪声淹没；max 档每 100 题要几十元，预算撑不起多张消融表。
  - 别名会被百炼静默升级到新版本，同一张对比表里前后跑的实验可能用了不同的模型。固定快照名才能保证可比。
  - 3.7-plus 准确率显著更高（+11 个百分点，p = 0.035），更接近论文 GPT-5-mini 的水平，和论文的消融结论更有可比性；每 100 题 6.2 元，在预算内能跑完阶段 1 的整张对比表。
- **代价与局限**：快照会下线，届时需要整表重跑。与论文的 GPT-4o-mini / GPT-5-mini 不是同一个模型，绝对数值不能直接对比，只能比相对趋势。3.7-plus 每题成本约为 plus-1201 的 2.8 倍，并且有 22% 的题跑满 15 轮，后续实验的成本和轮数上限都受它影响。

## D3. 关闭思考模式（`enable_thinking: false`）

- **背景**：Qwen 新模型是混合思考模型，开启思考后输出变贵，而且部分模型要求流式输出；上游 `LLMClient` 是非流式的。
- **备选方案**：开启 / 关闭。
- **最终选择**：关闭，并且在配置里**显式**写 `enable_thinking: false`，不依赖各模型不同的默认值。
- **理由**：成本更低；上游客户端可以直接用；与论文的 GPT-4o-mini（非推理模型）那一列对应。轨迹里没有 reasoning_content，以后转 SFT 数据格式也更简单。
- **代价与局限**：可能低估模型能力。思考模式可以留作以后的一个单独消融实验。

## D4. 固定裁判模型，不随 Agent 模型变化

- **背景**：上游 `eval.py` 用 `ARAG_MODEL` 环境变量作为裁判，也就是 Agent 用什么模型，裁判就用什么模型。论文固定用 GPT-5-mini 当裁判。
- **备选方案**：沿用上游（裁判 = Agent 模型）/ 固定一个裁判。
- **最终选择**：配置里单独的 `judge` 段，固定为 qwen-plus 快照，非思考模式，温度 0，`max_tokens=16`。
- **理由**：裁判是“尺子”。换 Agent 模型时如果尺子也跟着换，准确率的变化就分不清是 Agent 变了还是尺子变了。
- **代价与局限**：裁判与 Agent 是同一个模型时，可能存在“自己给自己打分”的偏差。上游裁判要求回复恰好是 `correct`，格式略有偏差就会误判。因此 `judge_meta.json` 记录了裁判回复的分布，用来检查有没有误判。

## D5. 成本统计口径：标价、人民币、计入隐式缓存

- **背景**：上游价格表没有 Qwen，而且是美元。百炼按单次请求的输入长度分档计价，隐式缓存命中的 token 按输入单价的 20% 计费，另有免费额度和限时折扣。
- **最终选择**：`configs/pricing_bailian.yaml` 按快照名记录分档标价（注明来源和核实日期），按每次请求的 `prompt_tokens` 选档，缓存部分乘 0.2。免费额度和限时折扣不计入。
- **理由**：按标价算出的是**上界**，在不同时期跑的实验之间可比，不受折扣活动影响。缓存折扣是 Agent 场景的真实特性（每轮重发相同前缀），必须计入，否则会高估成本。
- **代价与局限**：与阿里云账单上的实际扣费会有差距（免费额度期间账单可能是 0）。价格调整时需要更新 YAML。

## D6. LLM 调用失败时带退避重试

- **背景**：上游 `BaseAgent` 遇到 LLM 异常直接 `break`，随后强制作答，结果被标成“达到最大轮数”。并发跑题时偶发的 429 限流会让这道题直接变成错题。
- **最终选择**：对 429 / 5xx / 超时 / 连接错误做指数退避重试（基数 2 秒，最多重试 4 次，带随机抖动）；4xx 参数错误立即失败。最终失败的调用记入 `llm_errors`，终止原因标为 `llm_error`。
- **理由**：瞬时的基础设施错误不应该算作 Agent 的能力问题。
- **代价与局限**：重试会拉长那道题的耗时，延迟统计里会包含重试等待的时间。

## D7. 评测子集：均匀随机抽样，固定种子，并且与调试集不相交

- **背景**：预算限制下不能每次都跑完整的 1000 题。
- **备选方案**：取前 100 题 / 随机抽样 / 按跳数分层抽样。
- **最终选择**：从 1000 题中用 `random.Random(42)` 抽 100 题，保持原顺序，文件和元数据（源文件 sha256、种子、题目 id）一起提交到 `data/subsets/`。调试用的 5 题子集（种子 7）与这 100 题不相交。
- **理由**：数据集的顺序可能有偏（前面的题可能集中在某种题型），取前 100 题不可靠；固定种子加源文件哈希，任何人都能复现同一个子集；调试集与评测集分开，可以避免在评测集上调参。
- **代价与局限**：没有分层，100 题里 4 跳题只有 11 道（全量中占 16.6%），按跳数细分时样本太少。100 题的准确率标准误大约是 ±5 个百分点，差距小于这个量级的结论不可靠。

## D8. 本地 GPU 环境：固定 torch 的 CUDA 12.8 构建

- **背景**：Windows 驱动 572.70 最高支持 CUDA 12.8；`uv sync` 默认装的 torch 2.15 是 CUDA 13.2 构建，WSL2 中 `torch.cuda.is_available()` 为 False。
- **备选方案**：升级 Windows 显卡驱动 / 固定旧版 torch。
- **最终选择**：在 `pyproject.toml` 里把 torch 指向 PyTorch 官方 cu128 源（得到 torch 2.11.0+cu128）。
- **理由**：不需要改动 Windows 系统，可复现；cu128 构建在更新的驱动上也能运行。
- **代价与局限**：torch 停在 2.11。以后需要较新的 vLLM（阶段 7）时可能还是得升级驱动，届时去掉这个固定。

## D9. 主指标用 LLM-Acc，Cont-Acc 只作参考

- **背景**：上游同时报告 LLM-Acc（LLM 裁判）和 Cont-Acc（标准答案是否是预测的子串）。阶段 0 中两者相差 13 个百分点，方向与论文相反。
- **做法**：人工核对了全部 42 道两种指标结论不一致的题（experiments.md 阶段 0 一节）。
- **发现**：裁判在 83% 的分歧题上判断正确，错误都是“过严”，没有把错答案判对的情况；Cont-Acc 因为答案啰嗦（中位数约 1000 字符），在 35 道分歧题中大多是误判为对。
- **最终选择**：以 LLM-Acc 为主要指标，所有结论基于它得出；Cont-Acc 照常报告，但不用来下结论。
- **理由**：一个指标首先要验证它能不能“量准”。Cont-Acc 的误判与答案长度相关，而阶段 5 的改动（例如规划、笔记）很可能改变答案长度，用它做对比会把“答案变长”误当成“变准了”。
- **代价与局限**：LLM 裁判有成本（每 100 题约 0.03 元，可以忽略），并且约低估 2–3 个百分点。如果以后要让 Cont-Acc 可用，可以让 Agent 额外输出一个简短的“最终答案”字段。但这会改动上游提示词，留到阶段 1 再评估。

## D10. 普通 RAG 基线：照论文实现，块级向量单独建索引

- **背景**：阶段 1 需要一个“一次向量检索取 top-k，再生成答案”的基线。上游仓库没有提供基线脚本（README 的 TODO 里列着）。论文对 Naive RAG 的描述是：Qwen3-Embedding-0.6B、top-k = 5、约 1000 token 的块、Figure 6 的提示词模板，没有说明块怎么拼接。
- **备选方案**：
  1. 复用 A-RAG 的句子级索引，取每个块里最相似句子的分数作为块的分数；
  2. 对整块文本单独建一份块级向量索引；
  3. 让 A-RAG 只保留 semantic_search 一个工具（这是另一种东西，论文叫 A-RAG (Naive)，仍然是 Agent）。
- **最终选择**：方案 2。整块编码，归一化，不加 query instruction（与上游 `build_index.py` 和 semantic_search 一致），缓存在 `data/musique/index/chunk_index.npz`，元数据里记录模型名和 chunks.json 的哈希，任一变化就重建。提示词按 Figure 6：第一句作为 system，其余作为 user；块按 `[Chunk id]\n正文` 用空行拼接。代码：`research_agent/baselines/naive_rag.py`。
- **理由**：“普通 RAG”的通行做法就是块级检索，论文报告的 Naive RAG 检索量（MuSiQue 5,387 token）也正好约等于 5 个整块（我们的块平均 1,079 token）。方案 1 实际上是把 semantic_search 的排序拿来用，会让基线和 A-RAG 共享同一个检索器，削弱对比的意义。
- **代价与局限**：多了一份索引（1,354 × 1024 维，约 5.5 MB）。块级向量对约 1000 token 的长文本是“平均语义”，可能不如句子级精确，这正是论文想说明的问题之一，但也意味着基线的强弱依赖嵌入模型对长文本的处理能力。为了不在 6 GB 显存上加载第二份嵌入模型，基线复用 semantic_search 已加载的模型（`shared_semantic_tool`）。

## D11. 工具消融：配置开关，提示词和工具描述跟着工具集走

- **背景**：论文的消融有三个：w/o Keyword Search、w/o Semantic Search（直接去掉对应工具），w/o Chunk Read（“把两个搜索工具的片段结果换成完整块文本，并去掉 read_chunk”）。上游没有提供消融接口，系统提示词里写死了三个工具名。
- **备选方案**：
  1. 只在注册表里少注册一个工具，提示词不动；
  2. 少注册工具，同时从提示词里删掉对应的那一行；w/o Chunk Read 再改策略句和搜索工具的返回说明。
- **最终选择**：方案 2，开关是 `agent.tools` 和 `agent.search_result: snippet | full_chunk`。提示词由上游文件派生（`research_agent/agent/prompt.py`），每处修改都断言目标文本存在，上游提示词一变就报错；完整配置下输出与上游文件逐字节相同（有单元测试）。w/o Chunk Read 用包装器 `FullChunkSearch` 实现（`research_agent/agent/tools.py`）：排序仍交给上游搜索工具，只把结果换成整块文本。另外两个细节：
  - **全文去重**：已经展示过全文的块再次命中时，只返回“之前已展示”的标记，和上游 read_chunk 的去重逻辑一样。这样 w/o Chunk Read 与完整版的唯一差别是“全文由谁挑选”（搜索排序 vs 模型），而不是“有没有去重”。论文没有说明这一点。
  - **缺索引报错**：上游在找不到句子索引时会静默去掉 semantic_search，这会让完整版在不知不觉中变成消融版。这里改为直接报错。
- **理由**：提示词里列出一个不存在的工具，模型可能会去调用它，得到 “Tool not found” 后浪费轮数，测出来的就不只是“少一个工具”的效果了。消融只应改变一个变量。
- **代价与局限**：其余工具描述里仍然提到被去掉的工具（例如 semantic_search 的描述写着“当关键词搜索失败时使用”），只删除了提示词里的工具列表行，没有逐句改写所有描述。这是为了让改动尽量小，也和论文“直接去掉工具”的说法一致。

## D12. 一张对比表里的实验靠构造保证可比

- **背景**：工作规则要求同一张表里的实验必须使用相同的模型和参数。手工维护多份配置文件很容易漏改某个参数。
- **最终选择**：用“实验套件” YAML（`configs/suites/`）描述一整张表：每个变体 = 一个基础配置 + 少量覆盖项。生成对比表时（`research_agent/eval/compare.py`），从每个运行目录的 `run_meta.json` 里读出完整配置，展开后逐项比较：只允许 `method`、`agent.tools`、`agent.search_result`、`naive_rag.*` 不同；模型快照、温度、轮数上限、题目文件哈希、并发数等任何一项不同，都直接报错。表格下方列出每一行与其他行不同的设置。
- **理由**：可比性由数据检查保证，不靠人记。这项检查也能防住“重跑时换了模型别名”或“用错了子集”这类错误。
- **代价与局限**：代码版本（git commit）允许不同，只在表格里注明。阶段 0 的旧运行可以直接放进表里（在套件里写 `run_dir`），前提是这些运行的配置通过上面的检查。

## D13. 对比用全部题目上的 LLM-Acc，配对做精确 McNemar 检验

- **背景**：100 题上单个准确率的 95% 置信区间约为 ±9 个百分点，而论文里的消融差距只有 0.5–4.7 个百分点。两个准确率的置信区间是否重叠，并不是判断差异的正确方法：同一批题目上的两次运行是配对数据。
- **最终选择**：
  - 对比表里的准确率用“全部题目”作分母（`llm_acc_all`），空答案和报错都算错。上游 `eval.py` 的分母只算有答案的题，会让报错多的变体占便宜。阶段 0 两次运行都没有报错，两种口径相同。
  - 每个变体都与参考行（A-RAG Full）逐题配对，只看“一个对、一个错”的题，做双侧精确 McNemar 检验，报告 p 值和两类不一致题的数量。
- **理由**：配对检验消除了“题目难度”这个最大的方差来源，比两个独立比例的检验灵敏得多。精确检验适用于不一致题很少（几道到十几道）的情况。
- **代价与局限**：100 题仍然只能可靠地检出约 10 个百分点以上的差距。表中 p > 0.05 的差异只能说明“没有检出”，不能说明“没有差异”。要验证论文中几个百分点的消融差距，需要更大的子集（例如 300 题，花费约为 3 倍）。

## D14. 新指标的口径：重复读取率与重复检索率

- **背景**：方案要求统计“重复读取率：同一文本块被重复读取的比例”。
- **最终选择**：
  - **重复读取率** = 请求全文时，已经展示过全文的块数 ÷ 请求全文的块总数，在全部题目上合并计算（微平均）。完整版的“请求全文”是 read_chunk；w/o Chunk Read 版本是返回全文的搜索。两者都记录 `new_chunks_count` 和 `already_read_count`，所以用同一个公式计算。
  - 另外增加 **重复检索率**：同一题内，与之前某次搜索完全相同的搜索（同一工具、关键词集合或查询文本相同、top_k 也相同，忽略大小写和空白）所占的比例。这对应阶段 2 bad case 标签里的“重复检索”。
  - **达到最大轮数的比例** 只统计 `termination == max_loops`，LLM 报错导致的提前结束单独记为 `llm_error`（D6）。
  - 按跳数分组的准确率从 MuSiQue 题目编号里解析（`musique_3hop1__…`）。
- **理由**：上游 read_chunk 对已读的块只返回一句提示，不会重复计入 retrieved tokens，因此“重复读取”在上游指标里是看不见的，但它仍然浪费一轮 LLM 调用。阶段 0 的数据显示，3.7-plus 有 8.3% 的读块请求读的是已经读过的块。
- **代价与局限**：重复检索只识别完全相同的搜索。换个说法再搜一遍同一件事（语义重复）不会被计入，需要等阶段 2 的轨迹分析来补充。另外，w/o Chunk Read 版本的“重复读取”是搜索结果再次命中已展示的块，由排序决定，不是模型主动重读，而且这些块不重复计 token。它和完整版的重复读取率含义不同，不能直接比较（阶段 1 中两者分别为 31.3% 和 9.7%）。

## D15. 暂不做 LLM 响应缓存（方案中的可选项）

- **背景**：方案把“相同请求不重复计费的响应缓存”列为可选项。
- **最终选择**：阶段 1 不做。
- **理由**：
  1. 对比表里的每个变体请求都不同，缓存命中不了；
  2. 中断后续跑已经由上游 BatchRunner 的断点续跑（跳过已完成的题目）解决，判分和汇总可以单独重跑，不调用 Agent；
  3. 缓存命中会让延迟和花费指标失真，需要额外区分“真实调用”和“缓存命中”。
- **代价与局限**：如果以后需要反复重放同一批请求（例如阶段 2 调试轨迹回放、阶段 5 修改汇总逻辑），再按 payload 哈希加一层磁盘缓存，并在记录里标记命中。D9 中提到的“让 Agent 额外输出简短最终答案以改善 Cont-Acc”，阶段 1 也不做：它需要修改提示词，会让结果与论文和阶段 0 不可比。

## D16. 内容审核拦截按答错计，另做排除后的敏感性分析

- **背景**：阶段 1 的 w/o Chunk Read 变体有 5 道题的请求被百炼内容审核拦截（HTTP 400 `DataInspectionFailed`）。这时 Agent 循环中断，强制作答也被拦截，最终输出 `Error: ...`。其他变体一次都没有被拦截。
- **备选方案**：
  1. 按答错计入主表；
  2. 从所有变体中剔除这 5 题，主表只用剩下的 95 题；
  3. 换一个审核更宽松的模型重跑这几题。
- **最终选择**：方案 1 作为主表口径，同时报告方案 2 的结果作为敏感性分析（experiments.md 阶段 1 一节）。客户端不对 400 重试（D6 的规则不变）。
- **理由**：被拦截是“整块返回”这个设计在国内云 API 上真实会遇到的失败：上下文里堆了大量原文，更容易触发审核。把它算作失败，才反映该设计在这个部署环境下的真实表现。剔除这些题则相当于只在“对它友好”的题上比较。方案 3 换了模型，违反同一张表用同一模型的规则。
- **代价与局限**：主表里 w/o Chunk Read 的准确率包含了平台因素，并不是纯粹的“检索接口”效应。排除这 5 题后，结论从“低 2 个百分点”变成“高 2 个百分点”，两者都不显著。审核的具体触发规则不透明，换一个时间或换一个快照，结果可能不同。阶段 6 的服务需要处理这类错误：向用户返回明确的“内容被平台拦截”，而不是笼统的报错。
