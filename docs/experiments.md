## 2026-10-30 · 环境检查与 MuSiQue 索引构建

- **环境**：WSL2 Ubuntu（内核 6.18），Python 3.12.3，uv 0.12.23；WSL 可用内存 7 GB，16 核。
- **GPU**：NVIDIA GeForce RTX 3060 Laptop GPU，**显存 6144 MiB**（6.0 GiB），sm_86；Windows 驱动 572.70（支持 CUDA ≤ 12.8）。
- **PyTorch**：默认安装的 torch 2.15.0+cu132 无法使用 GPU（驱动太旧），改用 torch 2.11.0+cu128 后 `torch.cuda.is_available() == True`，矩阵乘法验证通过（见 upstream_changes.md）。
- **索引构建**（上游 `scripts/build_index.py`，参数与 README 相同）：

| 项目 | 数值 |
| --- | --- |
| 嵌入模型 | Qwen/Qwen3-Embedding-0.6B（1024 维，fp32） |
| 块数 / 句子数 | 1,354 / 50,767 |
| batch size | 32（脚本默认值） |
| 耗时 | 4 分 26 秒（含模型下载） |
| 峰值显存 | 约 3.1 GB（nvidia-smi 采样） |

- **结论**：6 GB 显存下 batch 32 留有约 3 GB 余量。之后语料更大时，内存（WSL 7 GB）比显存更早成为瓶颈：pickle 索引会整体加载到内存中。

## 2026-10-30 · 冒烟测试与主模型选型（dev5）

- **目的**：验证“运行 → 裁判 → 汇总”全流程，并比较两个 plus 档候选模型的成本和行为。**样本只有 5 题，准确率差异没有统计意义，不能用于下结论。**
- **数据**：`data/subsets/musique_dev5_seed7.json`（5 题，与 100 题评测集不相交）。
- **公共配置**：A-RAG (Full) 三个工具，`max_loops=15`，`max_token_budget=128000`，temperature 0，`max_tokens=16384`，`enable_thinking=false`，5 并发；裁判固定为 qwen-plus-2025-12-01。
- **配置文件**：`configs/musique_qwen_flash_debug.yaml`、`configs/musique_qwen_plus.yaml`、`configs/musique_qwen37_plus.yaml`。

| 指标 | qwen-flash（调试） | qwen-plus-2025-12-01 | qwen3.7-plus-2026-05-26 |
| --- | --- | --- | --- |
| LLM-Acc / Cont-Acc | 1/5 / 1/5 | 3/5 / 3/5 | 4/5 / 4/5 |
| 平均轮数 / 工具调用次数 | 4.6 / 3.6 | 7.8 / 7.0 | 10.0 / 9.2 |
| 工具调用分布（keyword / semantic / read，次/题） | 1.0 / 1.8 / 0.8 | 4.2 / 1.4 / 1.4 | 4.8 / 1.8 / 2.6 |
| 平均输入 / 输出 token | 13,474 / 403 | 38,955 / 1,976 | 74,620 / 1,292 |
| 隐式缓存命中率 | 14.5% | 0.0% | 75.6% |
| 平均 retrieved tokens（上游指标） | 3,283 | 4,451 | 8,050 |
| 延迟 平均 / P50 / P95（秒） | 13.7 / 9.7 / 28.1 | 65.8 / 69.9 / 114.8 | 63.5 / 73.8 / 103.4 |
| 终止原因 | 全部正常作答 | 正常作答 4，max_loops 1 | 正常作答 4，max_loops 1 |
| 花费（元，Agent + 裁判） | 0.0130 | 0.1773 | 0.3486 |

**观察**：
1. 流程正确：裁判的 15 次回复都是规范的 `correct` / `incorrect`，没有出现因格式被误判的情况；没有 API 报错。
2. qwen-plus-2025-12-01 的所有调用返回的 `cached_tokens` 都是 0，即这个快照实际上没有享受到隐式缓存折扣。尽管如此，它每题的花费仍然只有 qwen3.7-plus 的一半。
3. qwen3.7-plus 搜索得更久，成本呈长尾分布：一道两个模型都答错的 2 跳题，它跑满 15 轮，单题输入 19 万 token。
4. flash 平均 3 轮就作答，常见的失败方式是“检索一次没找到就宣布资料里没有”，属于“过早停止”类 bad case。
5. **决定**：两个 plus 模型都在 100 题上跑一遍，用正式结果确定主模型（见下一节）。

### 裁判可靠性核查

两个模型的 Cont-Acc 都比 LLM-Acc 高 13 个百分点，与论文的情况相反（论文中 LLM-Acc ≥ Cont-Acc）。我人工核对了**全部 42 道两种指标结论不一致的题**：

| | plus-1201 | 3.7-plus | 合计 |
| --- | --- | --- | --- |
| 预测包含标准答案，但裁判判错 | 16 | 19 | 35 |
| 预测不包含标准答案，但裁判判对 | 3 | 4 | 7 |
| 人工判定：裁判正确 | 15 | 20 | 35（83%） |
| 人工判定：裁判错误（均为过严） | 2 | 3 | 5（12%） |
| 存疑 | 2 | 0 | 2（5%） |

- **裁判的错误都是“过严”**：没有发现把错答案判成对的情况。典型错误：预测 “500 mA”、标准答案 “five unit loads”（两者等价，且预测原文写了 “five unit loads”）；预测 “major professional sports league”、标准答案 “sports league”；预测 “Wittenberg, in the east of Saxony-Anhalt”、标准答案 “Saxony-Anhalt”。
- **Cont-Acc 严重虚高**：答案长度的中位数约 1000 字符，常见情况包括：预测列举多个候选，碰巧提到了标准答案；或者最终声明“资料里找不到”，但推理过程中出现过标准答案。在 35 道“包含但被判错”的题中，大多数预测确实是错的。
- **据此估计的“真实”准确率**：plus-1201 约 59–61%，3.7-plus 约 71%。裁判约低估 2–3 个百分点，对两个模型的影响方向一致，不影响比较结论。
- **结论**：后续以 LLM-Acc 为主要指标；Cont-Acc 只作参考，不用于下结论（见 design_decisions.md D9）。

### 与论文对比（MuSiQue，A-RAG Full）

| 来源 | 模型 | LLM-Acc | Cont-Acc | retrieved tokens |
| --- | --- | --- | --- | --- |
| 论文 | GPT-4o-mini | 46.1 | 39.6 | — |
| 论文 | GPT-5-mini | 74.1 | 65.3 | 5,663 |
| 本次 | qwen-plus-2025-12-01（非思考） | 57.0 | 70.0 | 2,946 |
| 本次 | qwen3.7-plus-2026-05-26（非思考） | 68.0 | 83.0 | 7,366 |

**差异分析**：
1. **LLM-Acc 落在论文两种骨干模型之间**，符合预期：非思考模式的 Qwen plus 档强于 GPT-4o-mini，弱于推理模型 GPT-5-mini。代际更新的 3.7-plus 已接近 GPT-5-mini（差 6 个百分点，在 100 题的置信区间内）。
2. **Cont-Acc 远高于论文**：主要原因是 Qwen 的答案更啰嗦（系统提示要求引用 chunk、给出证据），包含匹配更容易命中。这也是 Cont-Acc 不可靠的原因。
3. **裁判不同**：论文用 GPT-5-mini，我们用 qwen-plus-2025-12-01。核查显示我们的裁判略严，大约低估 2–3 个百分点。
4. **子集不同**：论文应是全部 1000 题，我们是 100 题，统计误差约 ±9 个百分点。我们子集中 4 跳题占 11%（全量为 16.6%）。
5. **参数**：论文没有给出 max_loops 和温度；我们用 15 轮（`configs/example.yaml` 的值）、温度 0。3.7-plus 有 22% 的题达到 15 轮上限，说明这个参数对它有实际影响。
6. **相同的部分**：语料、嵌入模型（Qwen3-Embedding-0.6B）、提示词、工具实现、top_k 默认值都与论文一致。

### 其他观察（留给阶段 4 bad case 分析）

- **两个模型的失败方式不同**（按关键词粗略统计）：3.7-plus 的 32 道错题中，有 14 道是“资料里找不到”式的放弃作答；plus-1201 的 43 道错题中只有 6 道是放弃作答，其余多是给出一个确定但错误的答案，有时还会用模型自身知识补全（例如 “Voyager 2 于 2018 年离开太阳系”）。
- 3.7-plus 有 22% 的题跑满 15 轮。这些题的准确率只有 7/22，而且是成本的主要来源（花费最高的 10% 题目占总花费的 26%）。“何时停止”是一个明确的改进方向（对应阶段 5a 的“信息是否充分”判断）。
- 3 跳题明显最难（plus-1201 只有 38%）。4 跳题只有 11 道，样本太少，不做解读。

## 2026-10-30 · 阶段 1 冒烟测试：基线与消融套件（dev5 · qwen-flash）

- **目的**：在花钱跑 100 题之前，验证普通 RAG 基线、三个工具消融、汇总和对比表的全流程。**5 题、调试模型，准确率不能用于下结论。**
- **命令**：`python -m research_agent.eval suite configs/suites/stage1_dev5_flash.yaml`（基础配置 `configs/musique_qwen_flash_debug.yaml`，题目 `data/subsets/musique_dev5_seed7.json`）。
- **结果目录**：`results/dev/stage1_dev5_flash/`（不进版本库），对比表在 `comparison.md` / `comparison.csv`。
- **块级向量索引**（普通 RAG 用，首次运行时自动构建）：1,354 块 × 1024 维，`data/musique/index/chunk_index.npz`，5.6 MB。

| 变体 | LLM-Acc | 轮数 | 工具调用（kw / sem / read） | 重复读取率 | 平均输入 token | retrieved tokens | 花费（元，Agent + 裁判） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 普通 RAG | 1/5 | 1.00 | 一次稠密检索 | — | 5,784 | 5,306 | 0.0055 |
| A-RAG (Full) | 1/5 | 3.40 | 1.00 / 0.40 / 1.00 | 0.0% | 6,911 | 1,564 | 0.0074 |
| w/o keyword | 1/5 | 3.80 | 0 / 1.60 / 1.20 | 5.6% | 8,916 | 3,805 | 0.0099 |
| w/o semantic | 2/5 | 5.20 | 2.60 / 0 / 1.60 | 25.0% | 18,349 | 3,229 | 0.0168 |
| w/o read_chunk | 0/5 | 2.40 | 1.00 / 0.40 / 0 | 3.2% | 12,439 | 6,444 | 0.0119 |

**观察**：
1. 全流程跑通，没有 API 报错；裁判回复全部是规范格式。对比表的可比性检查通过：5 行只在 `method`、`agent.tools`、`agent.search_result` 上不同。
2. 普通 RAG 每题检索 5,306 token，与论文报告的 5,387 吻合，说明“top-5 整块”的实现与论文一致。
3. w/o read_chunk 的检查：搜索结果确实是整块全文，重复命中的块被标记为“之前已展示”，没有重复计入 token。flash 在这个变体下平均只搜 1.4 次就作答，5 题全错，属于“看到大段文本就以为信息够了”的过早停止。
4. **同一配置的两次运行并不相同**：A-RAG (Full) + flash 在阶段 0 平均 4.6 轮、本次 3.4 轮（温度都是 0）。这说明 API 侧有非确定性，也是正式评测里重跑一次完整版、用来测量随机波动的原因。
5. **正式评测的费用估算**（已获批准）：用阶段 0 的 3.7-plus 轨迹离线重放“搜索返回整块”的情形。重放方法在 snippet 模式下与实际输入 token 的误差为 4%；结果显示 w/o read_chunk 每题输入约 16.7 万 token，是原版的 2.5 倍，100 题约 14 元。整个套件约 37 元。
