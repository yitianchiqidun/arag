# 项目成果摘要

截至 2026-11-03。项目：基于 A-RAG 的 TiDB 运维诊断助手（分支 `stage-3-tidb`）。每个数字后面注明出处文件和日期，`results/` 下的原始运行结果不进版本库，汇总表都在 `docs/` 下。设计决策编号（D1–D36）指 `docs/design_decisions.md`。

## 一、项目概况

- **做了什么**：
  1. 在百炼 Qwen 模型上复现 A-RAG（分层检索 Agent）。
  2. 把它接到 TiDB 官方中文文档上，做带引用的参数和版本问答。
  3. 再加上只读集群工具和需要确认的写操作，做成一个能诊断本地 TiDB 集群故障的 LangGraph Agent。
  4. 用 FastAPI + SSE 对外提供服务。
- **技术栈**：
  - Python 3.12、LangGraph 1.2.19（`interrupt()` 人工确认、SQLite 检查点）、FastAPI + SSE、Streamlit；
  - Qwen3-Embedding-0.6B（本地 GPU）、百炼 qwen3.7-plus / qwen3.7-flash；
  - TiDB v8.5.8（tiup playground）、pymysql、pydantic、pytest、ruff、mypy。
- **规模**：
  - 本项目代码（`research_agent/`）约 1.09 万行，测试约 5,100 行，演示页约 850 行；
  - 240 个测试（236 个默认运行，4 个连接真实集群、需 `TIDB_LIVE=1`），测试中的模型和数据库都是假的；
  - 分支上约 60 个提交，36 条设计决策记录。
  - A-RAG 原有的 Python 源码没有改动（`docs/upstream_changes.md`）。
- **API 花费**：10 月 41.98 元，11 月（截至 11-03）21.45 元，其中 6.07 元是已废弃的实验（`docs/experiments.md` 台账）。

## 三、负面结论（做了但没有效果，或被数据否定）

1. **强制作答保留工具 + `tool_choice="none"` 不能命中缓存**（D34）。
   - 百炼此时会去掉工具定义，提示前缀变了：缓存命中 0%（5 段对话），不省钱。
   - 真正的原因是上游强制作答新开了一条用户消息，Qwen3 模板会因此改变之前所有助手轮次的渲染方式。
   - 把指令附在最后一条工具结果里，缓存命中 97%、花费降 79%，但 3 次中有 2 次模型仍调用工具，所以不采用。
2. **快通道在 TiDB 评测集上省不了多少钱**（D32）。普通 RAG 每次把 5 个整块放进提示，几乎不命中缓存；A-RAG 读得少，又有 63% 的缓存命中。全部 126 题上普通 RAG 只便宜 21%（每 100 题 1.08 vs 1.37 元）；在被分到快通道的 96 道参数题上只便宜约 9%（每题 0.0108 vs 0.0118 元），加上分类器后分流方案的总花费与全部 A-RAG 相同，准确率却低 14 个百分点。
3. **工具消融在 100 题上分辨不出来**（D13、D17）。差距 2–5 个百分点，和同一配置重跑的波动同一量级。
4. **评测集对 A-RAG 太简单**：A-RAG 在 126 题上 100%，只能衡量快通道少答对多少，区分不了 A-RAG 自身的改进。
5. **要求诊断引用文档，代价很高**（D35）：诊断中的开放式文档检索每次约 130 秒、0.13–0.18 元，第二轮场景的花费是首轮的 7 倍。
6. **整块返回会触发内容审核**：去掉 read_chunk 后，有 5 道 MuSiQue 题被百炼内容审核拦截（HTTP 400），其他变体一次都没有被拦截。

## 四、已知局限

- **评测规模和可靠性**：
  - MuSiQue 只用 100 题子集（单次准确率的置信区间约 ±9 个百分点）；
  - TiDB 评测集没有人工复核；
  - 裁判有少量误判（MuSiQue 上偏严约 2–3 个百分点；TiDB 上有 2 例把与标准答案一致的简短回答判错，`docs/bad_cases.md` 第 2 条）。
- **故障场景**：
  - 只有 4 个，**每个诊断场景只跑了一次**（首轮、第二轮各一次），没有重复运行，单次结果受模型随机性影响；示例库只有 3 万行订单；
  - 诊断是否正确用关键词规则判断，模拟用户只批准参考修复；
  - **分类器测试集中手写的 30 道题由开发中使用的 AI 编程助手（Claude）编写**，分类提示词也由它修改，不是来自真实用户；测试集只有 50 题。提示词只改了一次、跑了一次，没有针对测试集反复调整。
- **诊断行为**：
  - 已经查到根因后仍继续探索，演示页的 4 次诊断都用满了 12 步，没有提出修改（`docs/bad_cases.md` 第 7 条）。现在步数用完时会强制给出结论，但只能写出建议语句。
  - 确认执行修改后，最终回答有时不复述根因（第 6 条）。
  - 曾因工具表格格式读错列而编造“索引不可见”，已修正格式（第 4 条，D36）。
- **检索**：
  - 稠密检索分不清相近的版本号（第 1 条）；
  - 参数题的引用有时偏向不相关的文档（例如 `explain-joins.md`）；
  - 证据检查只看有没有引用，不检查引用是否支持答案。
- **服务**：
  - 单进程，一次处理一轮，诊断吞吐约每 1–3 分钟一轮；
  - 超时后要等当前节点结束才释放。
- **部署验收的范围**：
  - Docker 只在一台机器（Docker Desktop + WSL2）上验收过；
  - 演示页是在容器内用 Streamlit 无头测试驱动的，没有在真实浏览器里操作；
  - 验收用的诊断问题直接点出了变量名，只用来走通写操作确认的流程。
- **没有实测**：
  - GitHub Actions（还没在 GitHub 上运行）；
  - 本地 vLLM 模型替换（只有配置和单元测试）。
- **延迟不能跨时段比较**：同一配置不同时段的 P50 可以相差 40%（阶段 1、2、7 都观察到）。

## 五、写简历时需要注意的说法

- “A-RAG 在 TiDB 评测集上 100%”要同时说明：评测集未经人工复核，题目对 A-RAG 偏简单。更有信息量的是“快通道比 A-RAG 低 16 个百分点，只便宜 21%；按意图分流后花费与全部 A-RAG 相同”。
- “复现 A-RAG”的准确说法：在 100 题子集上，A-RAG 相对普通 RAG 的优势（+25 个百分点，p < 0.001）与论文（+21.3）一致；绝对准确率比论文的 GPT-5-mini 低 3 个百分点，在置信区间内。
- 故障诊断的结果只能说成“4 个注入场景上 3/4 诊断正确、所有写操作都经过用户确认”，样本很小，每个场景只跑一次。
- 强制作答缓存实验是一个完整的负面结论，可以作为“用数据否定原方案、并找到根因”的例子。
