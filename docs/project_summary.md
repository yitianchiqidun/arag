# 项目成果摘要

截至 2026-11-03。项目：基于 A-RAG 的 TiDB 运维诊断助手（分支 `stage-3-tidb`）。每个数字后面注明出处文件和日期，`results/` 下的原始运行结果不进版本库，汇总表都在 `docs/` 下。设计决策编号（D1–D38）指 `docs/design_decisions.md`。

## 一、项目概况

- **做了什么**：
  1. 在百炼 Qwen 模型上复现 A-RAG（分层检索 Agent）。
  2. 把它接到 TiDB 官方中文文档上，做带引用的参数和版本问答。
  3. 再加上只读集群工具和需要确认的写操作，做成一个能诊断本地 TiDB 集群故障的 LangGraph Agent。
  4. 用 FastAPI + SSE 对外提供服务。
  5. 新增日志、配置、报告三个工具，并把全部工具做成 MCP server（stdio）。
  6. 加了统一的工具调用中间件（harness），以及诊断的停止判据和预算。
- **技术栈**：
  - Python 3.12、LangGraph 1.2.19（`interrupt()` 人工确认、SQLite 检查点）、FastAPI + SSE、Streamlit、MCP Python SDK 2.3（stdio）；
  - Qwen3-Embedding-0.6B（本地 GPU）、百炼 qwen3.7-plus / qwen3.7-flash；
  - TiDB v8.5.8（tiup playground）、pymysql、pydantic、pytest、ruff、mypy。
- **规模**：
  - 本项目代码（`research_agent/`）约 1.21 万行，测试约 5,400 行，演示页约 850 行；
  - 253 个测试（249 个默认运行，4 个连接真实集群、需 `TIDB_LIVE=1`），测试中的模型和数据库都是假的；
  - 分支上约 70 个提交，38 条设计决策记录。
  - A-RAG 原有的 Python 源码没有改动（`docs/upstream_changes.md`）。
- **API 花费**：10 月 41.98 元，11 月（截至 11-03）22.26 元，其中 6.07 元是已废弃的实验（`docs/experiments.md` 台账）。

## 按简历口径的项目介绍

**TiDB 运维诊断助手**：基于 LangGraph 的数据库运维 Agent，能回答 TiDB 参数和版本问题并给出文档引用，也能连接集群诊断故障，修改集群前必须经过人工确认。

- **背景**：
  - TiDB 有上千个系统变量和配置项，每个版本都有默认值变化，排查故障又依赖经验。
  - 通用大模型不了解较新版本的变化：自建评测集中，版本变更题的闭卷可答率是 0%；它也看不到集群的实际状态。
  - 直接让模型操作数据库又有误改风险。
- **目的**：
  - 用官方文档回答参数和版本问题，答案能追溯到具体文档章节；
  - 用只读权限查看集群状态、定位根因；需要修改时只给出提议，由人确认后执行。
- **架构**（详见 `docs/architecture.md`）：
  - **编排层**：LangGraph 主图依次改写追问、分类意图（参数查询 / 跨文档研究 / 故障诊断 / 越界），然后分别进入文档检索、诊断循环或越界说明。修改提议用 `interrupt()` 暂停整张图等人确认；会话存在 SQLite 检查点里，支持多轮对话，进程重启后待确认的修改也不丢。
  - **检索层**：基于开源的 A-RAG 分层检索框架（关键词检索、语义检索、按块读取，由 Agent 多轮自主调用）。在它之上做的工作：
    - TiDB 中文文档的清洗、中文切句、按标题切块；
    - 增量索引，验证与全量构建逐块一致；
    - 答案引用的解析和校验，以及没写引用时的证据回退；
    - 把整个 A-RAG 封装成主 Agent 的一个文档检索工具；
    - 一个要求引用的普通 RAG 快通道作对照。
  - **工具层**：
    - 工具注册表标明每个工具的权限级别（只读 / 需确认 / 禁止）和开放给哪些意图；
    - 统一的调用中间件（harness）负责权限、参数校验、超时、截断、审计和每轮预算；
    - 工具可以在进程内执行，也可以经 MCP server（stdio）提供；MCP 只开放只读和“提议”类工具。
  - **数据库安全**：
    - 只读工具用只有查询权限的专用账号，并在真实集群上用 8 条写探测验证；
    - 配置读取用只有 CONFIG 权限的独立账号；
    - 写操作只能经人工确认后由 Agent 执行，并写审计日志。
  - **服务层**：FastAPI + SSE 流式接口、Streamlit 演示页、Docker Compose 部署（CPU 镜像）。
- **一次诊断的流程**：
  1. 用户描述症状，分类器判为诊断；
  2. 诊断循环调用只读工具（慢查询、执行计划、系统变量、锁等待、统计信息、日志、配置等），并检索官方文档作为依据；
  3. 查到能解释症状的证据就停下，提出修改（例如 `SET GLOBAL`、`ANALYZE TABLE`、建索引），整张图暂停；
  4. 用户在页面上确认后，Agent 用管理员账号执行，记录修改前后的状态；
  5. 最后按“现象 → 根因 → 依据 → 建议”给出结论和文档引用，也可以导出成 Markdown 报告。
- **工具清单**：
  - 文档检索 1 个（内部是 A-RAG 的 3 个分层检索工具）；
  - 集群只读 12 个；
  - 日志检索、配置查询、诊断报告各 1 个；
  - 修改提议 3 个（需确认）；
  - 登记为“禁止”的直接执行 1 个。
- **技术栈**：
  - Python、LangGraph、FastAPI / SSE、Streamlit、MCP Python SDK、pydantic；
  - Qwen3-Embedding-0.6B、通义千问（百炼）；
  - TiDB v8.5（tiup）、pymysql、Docker Compose；
  - pytest、ruff、mypy。

## 三、负面结论（做了但没有效果，或被数据否定）

1. **强制作答保留工具 + `tool_choice="none"` 不能命中缓存**（D34）。
   - 百炼此时会去掉工具定义，提示前缀变了：缓存命中 0%（5 段对话），不省钱。
   - 真正的原因是上游强制作答新开了一条用户消息，Qwen3 模板会因此改变之前所有助手轮次的渲染方式。
   - 把指令附在最后一条工具结果里，缓存命中 97%、花费降 79%，但 3 次中有 2 次模型仍调用工具，所以不采用。
2. **快通道在 TiDB 评测集上省不了多少钱**（D32）。普通 RAG 每次把 5 个整块放进提示，几乎不命中缓存；A-RAG 读得少，又有 63% 的缓存命中。全部 126 题上普通 RAG 只便宜 21%（每 100 题 1.08 vs 1.37 元）；在被分到快通道的 96 道参数题上只便宜约 9%（每题 0.0108 vs 0.0118 元），加上分类器后分流方案的总花费与全部 A-RAG 相同，准确率却低 14 个百分点。
3. **工具消融在 100 题上分辨不出来**（D13、D17）。差距 2–5 个百分点，和同一配置重跑的波动同一量级。
4. **评测集对 A-RAG 太简单**：A-RAG 在 126 题上 100%，只能衡量快通道少答对多少，区分不了 A-RAG 自身的改进。
5. **要求诊断引用文档，代价很高**（D35）：诊断中的开放式文档检索每次约 130 秒、0.13–0.18 元，第二轮场景的花费是首轮的 7 倍。
6. **整块返回会触发内容审核**：去掉 read_chunk 后，有 5 道 MuSiQue 题被百炼内容审核拦截（HTTP 400），其他变体一次都没有被拦截。

## 四、已知局限

- **评测规模和可靠性**：
  - MuSiQue 只用 100 题子集（单次准确率的置信区间约 ±9 个百分点）；
  - TiDB 评测集没有人工复核；
  - 裁判有少量误判（MuSiQue 上偏严约 2–3 个百分点；TiDB 上有 2 例把与标准答案一致的简短回答判错，`docs/bad_cases.md` 第 2 条）。
- **故障场景**：
  - 4 个默认场景，加上阶段 11 新增的 1 个，**每个诊断场景每轮只跑了一次**（首轮、第二轮、第三轮），没有重复运行，单次结果受模型随机性影响；示例库只有 3 万行订单；
  - 诊断是否正确用关键词规则判断，模拟用户只批准参考修复；
  - **分类器测试集中手写的 30 道题由开发中使用的 AI 编程助手（Claude）编写**，分类提示词也由它修改，不是来自真实用户；测试集只有 50 题。提示词只改了一次、跑了一次，没有针对测试集反复调整。
- **诊断行为**：
  - 已经查到根因后仍继续探索，演示页的 4 次诊断都用满了 12 步，没有提出修改（`docs/bad_cases.md` 第 7 条）。现在步数用完时会强制给出结论，但只能写出建议语句。
  - 确认执行修改后，最终回答有时不复述根因（第 6 条）。
  - 曾因工具表格格式读错列而编造“索引不可见”，已修正格式（第 4 条，D36）。
- **检索**：
  - 稠密检索分不清相近的版本号（第 1 条）；
  - 参数题的引用有时偏向不相关的文档（例如 `explain-joins.md`）；
  - 证据检查只看有没有引用，不检查引用是否支持答案。
- **阶段 10、11**：
  - harness 修复（需确认的工具不受调用预算拦截）之后没有再跑场景；
  - 重复检测只认完全相同的调用，换个工具查同一张表的结构认不出来；
  - 根因出现之前的探索仍可能很长；
  - `agent_cfg` 有 CONFIG 权限，理论上能 `SET CONFIG`，靠只发固定语句控制；
  - MCP 模式下嵌入模型加载两份；
  - 耗时对比跨了时段，受接口负载影响。
- **服务**：
  - 单进程，一次处理一轮，诊断吞吐约每 1–3 分钟一轮；
  - 超时后要等当前节点结束才释放。
- **部署验收的范围**：
  - Docker 只在一台机器（Docker Desktop + WSL2）上验收过；
  - 演示页是在容器内用 Streamlit 无头测试驱动的，没有在真实浏览器里操作；
  - 验收用的诊断问题直接点出了变量名，只用来走通写操作确认的流程。
- **没有实测**：
  - GitHub Actions（还没在 GitHub 上运行）；
  - 本地 vLLM 模型替换（只有配置和单元测试）。
- **延迟不能跨时段比较**：同一配置不同时段的 P50 可以相差 40%（阶段 1、2、7 都观察到）。

## 五、写简历时需要注意的说法

- “A-RAG 在 TiDB 评测集上 100%”要同时说明：评测集未经人工复核，题目对 A-RAG 偏简单。更有信息量的是“快通道比 A-RAG 低 16 个百分点，只便宜 21%；按意图分流后花费与全部 A-RAG 相同”。
- “复现 A-RAG”的准确说法：在 100 题子集上，A-RAG 相对普通 RAG 的优势（+25 个百分点，p < 0.001）与论文（+21.3）一致；绝对准确率比论文的 GPT-5-mini 低 3 个百分点，在置信区间内。
- 故障诊断的结果只能说成“4 个注入场景上 3/4 诊断正确、所有写操作都经过用户确认”，样本很小，每个场景只跑一次。
- 强制作答缓存实验是一个完整的负面结论，可以作为“用数据否定原方案、并找到根因”的例子。
